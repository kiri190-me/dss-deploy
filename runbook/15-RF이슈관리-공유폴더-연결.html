RF 이슈관리 — 공유폴더 연결

아홉째 사이트를 세운 뒤에 하는 일 · 작성 2026-10-22

■ 지금 상태 — RF 이슈관리(issues.dss21.co.kr)는 2026-10-22 18:58 에 NAS 에 섰고 잘 돌고 있습니다. 다만 공유폴더 둘을 일부러 안 붙였습니다 (「파일 위치는 배포판 이후에 시스템에서 고른다」 — 그날 결정).

이 문서는 그 둘을 붙이는 절차입니다. 서비스를 멈추지 않습니다 — 컨테이너 하나만 다시 띄우면 되고 몇 초입니다.

지금 무엇이 되고 무엇이 안 되나

안 되는 것 둘 자료 파일 열기·내려받기 — 검색에 이름은 그대로 나오는데 누르면 못 찾습니다 (색인은 data/ 안에 있어서 이름은 보입니다)
엑셀 자동 재색인 — 지금은 꺼 두었습니다(autoRefreshSec: 0)
되는 것이슈 등록 · 검색 · 주간보고 · 출장 일정 · 지식맵 · 첨부 — 전부 그대로

● 위 두 가지 말고 안 되는 것이 있으면 그건 공유폴더 탓이 아니라 진짜 고장입니다. 헷갈리지 않게 적어 둡니다.

붙이는 절차 — 네 걸음

1 · 실제 폴더 위치를 알아낸다 사람

지금 compose 에는 공유폴더 줄이 하나도 없습니다. 저장소의 원래 파일에는 /volume1/공유폴더A 같은 자리표시자만 있었습니다 — 실제 이름이 아닙니다.

NAS 에서 공유폴더 목록 보기:

ls -1 /volume1/

또는 DSM → File Station → 그 폴더 오른쪽 클릭 → 속성의 「위치」를 봅니다. /volume1/… 로 나옵니다.

알아내야 하는 것 셋:

공유폴더 A지금 윈도우에서 nas7 로 보이는 곳의 실제 위치
공유폴더 B지금 윈도우에서 nas1 로 보이는 곳의 실제 위치
업무정리 엑셀색인을 만드는 원본 한 장. 윈도우에서 보이는 \\…\…\파일.xlsx 꼴 그대로

2 · compose 에 두 줄 더한다 Claude

/volume1/dss/deploy/docker-compose.nas.yml 의 app-rf-trouble 블록 volumes: 아래에 두 줄을 더합니다.

volumes:
  - /volume1/dss/rf-trouble-data:/app/data
  - /volume1/dss/rf-trouble-data/config.json:/app/config.json:ro
  - /volume1/dss/rf-trouble-backup:/backup
  # 여기에 두 줄을 더한다
  - "/volume1/<실제 A>:/mnt/nas7:ro"
  - "/volume1/<실제 B>:/mnt/nas1:ro"

● :ro 를 빼지 마세요 — 읽기 전용입니다. 이 시스템이 직원 자료를 고칠 일이 없고, 고칠 수 있게 두면 언젠가 고쳐집니다.

● 오른쪽 이름(/mnt/nas7 · /mnt/nas1)은 3단계의 pathMap 오른쪽과 글자까지 같아야 합니다. 다르면 파일을 못 찾는데 오류가 안 납니다.

3 · config.json 을 채운다 Claude

/volume1/dss/rf-trouble-data/config.json 의 빈 칸을 채웁니다.

sourceExcel업무정리 엑셀의 UNC 경로
baseDir그 엑셀이 있는 폴더
scanDirs훑을 하위 폴더들 (예: 업무정리 엑셀에 인용한 자료 · 자료방)
pathMap UNC 경로 → 컨테이너 안 자리. 이 시스템은 윈도우 경로를 그대로 들고 있다가 이 표로 컨테이너 안 위치를 찾습니다
"\\\\<NAS-IP>\\<A>": "/mnt/nas7"
"\\\\<NAS-IP>\\<B>": "/mnt/nas1"
autoRefreshSec0 → 60 으로 되돌립니다 (이제 재색인할 원본이 생겼습니다)

고친 뒤 주인을 다시 맞춥니다:

chown 1026:100 /volume1/dss/rf-trouble-data/config.json
chmod 640 /volume1/dss/rf-trouble-data/config.json
ls -l /volume1/dss/rf-trouble-data/config.json

● 모드가 000 으로 서는 일이 실제로 있었습니다 (2026-10-22 설치 때). 주인만 보고 넘어가지 말고 -rw-r----- 인지 확인하세요.

4 · 다시 띄우고 값으로 확인한다 Claude

cd /volume1/dss/deploy
docker compose -f docker-compose.nas.yml --env-file .env.nas up -d --no-deps app-rf-trouble

● 인자 없는 up -d 를 부르지 마세요. 그러면 아홉 사이트가 전부 다시 뜹니다. --no-deps 로 이름을 적은 하나만입니다.

그다음 「붙었다」가 아니라 「읽힌다」를 봅니다:

# ① 볼륨이 실제로 붙었나 — 0 이 아니어야 한다
docker exec dss-rf-trouble sh -c 'ls -1 /mnt/nas7 | wc -l'
docker exec dss-rf-trouble sh -c 'ls -1 /mnt/nas1 | wc -l'

# ② 엑셀 원본에 실제로 닿나
docker exec dss-rf-trouble sh -c 'ls -l "$(node -e "console.log(require(\"/app/config.json\").sourceExcel)")" 2>&1 | head -1'

# ③ 살아 있나
curl -s http://127.0.0.1:13900/api/health
①0 이 아니어야 합니다. 0 이면 compose 의 왼쪽 경로가 틀린 것입니다
②파일 한 줄이 나와야 합니다. No such file 이면 pathMap 이 안 맞는 것입니다
③{"ok":true}

마지막으로 화면에서:

  1. 설정·정보 화면의 「자동 갱신」 칸에 실패가 없어야 합니다 (전에는 적혀 있었습니다)
  2. 검색에서 자료 파일을 눌러 실제로 열리는지
  3. 60초 기다렸다가 색인 수가 늘었는지

미리 알아 둘 것

권한 컨테이너가 1026:100(swhur / users)으로 돕니다. 시놀로지 공유폴더 권한은 이름 기반이라 users 그룹이어야 직원 폴더를 읽습니다 — 지금 그렇게 맞춰져 있어 준비는 돼 있습니다. 그래도 ①로 값을 확인하세요.
되돌리기 compose 사본이 /volume1/dss/backups/ 에 날짜별로 남습니다. 두 줄을 지우고 다시 띄우면 지금 상태로 돌아갑니다. 자료는 건드리지 않습니다(읽기 전용이라).
안 붙여도
안 깨진다		 코드로 확인했습니다 — 시작하는 길에 공유폴더를 보는 자리가 하나도 없습니다. 재색인은 쓰기 전에 죽어서 기존 색인(kb.json)을 덮어쓰지 않습니다. 그래서 중간에 실패해도 지금 있는 검색 결과가 사라지지 않습니다.
메모리 지금 18MiB / 512MiB 로 아주 가볍습니다. 공유폴더를 붙이면 색인을 만들 때 잠깐 늘어납니다. docker stats --no-stream 으로 재서 compose 맨 아래 예산표를 고쳐 둡니다.

● 이 시스템에는 비상구가 없습니다. 2026-10-21 에 팀 공용 비밀번호 로그인이 코드에서 걷혔습니다. 포털이 멈추면 아무도 못 들어옵니다 — 공유폴더 작업과는 무관하지만, 이 시스템을 만질 때마다 기억해 둘 일입니다.
