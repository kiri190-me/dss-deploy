## 1. 무엇이 지워지나

작업 하나가 **네 회차를 차례로** 돌린다. 앞의 셋은 `tools-as` 컨테이너로,
넷째는 **`tools-auth`** 로 부른다. 지우는 DB 도 성격도 다르다.

### ㄱ. A/S(+PO) 휴지통 — `tools-as` 세 회차 (`dss_as` DB)

| 회차 | 지우는 것 |
|---|---|
| `purge:repair-cases` | 휴지통 15일 지난 **수리 건** + 거기 딸린 **진단 순서도 전부**(따로 휴지통에 없어도 함께). 보존해야 하는 이력·회계 표 여섯은 `ON DELETE SET NULL` 로 **연결만 풀린다** |
| `purge:flowcharts` | 따로 휴지통에 넣은 **진단 순서도** (간선 → 마디 → 본체) |
| `purge:master-data` | **고객사**(담당자·End-User 까지) · **제품 모델** · **부품** · **기술 절차** · **내자 정리 줄** · **견적서** |

전부 **DB 안에서만** 지운다. 첨부 파일의 **디스크 실물은 건드리지 않는다**
(`master-data-purge.ts`: "첨부 행 · 디스크 실물은 남는다").

지운 자리마다 `audit_logs` 에 `PURGE` 한 줄이 남는다(`actor_user_id = NULL` —
사람이 아니라 시스템이 한 일). 다만 **연락처·이름 같은 개인정보는 그 스냅숏에
일부러 담지 않는다.** 즉 이 작업이 도는 순간이 그 개인정보가 시스템에서
영구히 사라지는 지점이다.

> 🔴 **PO 휴지통도 여기 딸려 있다.**
> PO(`dss-po`)는 A/S 와 **같은 `dss_as` DB** 를 본다. 견적서·발주·내자를
> A/S 에서 떼어 낸 사이트라 보는 표가 같다. 그래서 PO 에는 도구 이미지
> (`tools-po`)도 야간 작업도 없고, **PO 휴지통은 위 `purge:master-data` 가
> 함께 비운다**(`docker-compose.nas.yml` 의 `app-po` 머리말).
> 이것이 안 돌면 PO 휴지통도 영영 안 비워진다.

### ㄴ. 포털 다 쓴 행 — `tools-auth` 한 회차 (`dss_auth` DB, 2026-10-25 더함)

`dss-auth` 의 `scripts/purge-expired.ts` 가 다섯 표를 훑는다. 남기는 기간과
그 근거는 그 저장소 `src/lib/db/retention.ts` 에 있다(아래는 2026-10-25 실측).

| 표 | 남기는 기간 | 왜 그만큼인가 |
|---|---|---|
| `authorization_codes` | 만료 후 **7일** | `consumedAt` 표시가 남아 있어야 **재사용 공격과 단순 오타**를 구분할 수 있다 |
| `access_tokens` | 만료 후 **7일** | 인가 코드와 같은 기간 — 한 사건(코드 재사용 → 토큰 폐기)이 두 표에 걸쳐 남으므로 한쪽만 먼저 사라지면 안 된다 |
| `sso_sessions` | 만료·폐기 후 **30일** | 양이 적고, 「그때 누가 로그인해 있었나」는 나중에 물어보게 되는 질문이다 |
| `audit_logs` | 🔴 **3년** | ← **이 한 줄이 넷째 회차를 더한 까닭이다** |
| `notification_dismissals` | 지운 뒤 **하루** | 본래 길은 로그아웃이라 평소엔 0건. 로그아웃을 안 누르고 창만 닫은 경우를 걷는다 |

> 🔴 **감사 로그 3년을 집행하는 코드는 저것 하나뿐인데, 부를 길이 없었다.**
> 스키마 주석과 보안 정책 문서가 「3년 보관」을 선언해 두었는데 2026-10-25
> 까지 **한 번도 돈 적이 없었다** — 실제로는 영구 보관이었고 `source_ip` 와
> `user_agent` 를 의도보다 오래 들고 있었다. 0절에 적힌 A/S 의 일과 **같은
> 모양의 사고**다: 코드는 다 있는데 부르는 자리가 없었다.

> 🔴 **함정 — `audit_logs` 가 양쪽에 다른 뜻으로 나온다.**
> ㄱ 의 `audit_logs` 는 A/S(`dss_as`)에 `PURGE` 기록을 **남기는** 쪽이고,
> 여기 표의 `audit_logs` 는 포털(`dss_auth`)의 것을 **지우는** 쪽이다.
> **이름만 같고 DB 도 컨테이너도 다르다.** 한쪽을 고치면서 다른 쪽을
> 건드렸다고 생각하면 안 된다.

🔵 ㄱ 과 달리 이쪽은 휴지통이 아니라 **수명이 다한 행**이다. 사람이 「지운」
것이 아니라 되살려 달라는 요청이 올 일은 없다. 그래도 `DELETE` 라 문지기는
똑같이 씌운다(3절).

## 2. 🔴 보기만 하는 모드 — A/S 는 없고 포털은 있다

**A/S 세 스크립트 어느 것도 `--dry-run` 을 받지 않는다**(2026-09-29 확인 —
셋 다 `process.argv` 를 아예 읽지 않는다). `jobs/purge-nightly.sh` 에도 흉내만
낸 「보기만」 모드를 만들지 않았다. 그런 모드는 「봤으니 괜찮겠지」라는 잘못된
안심을 준다.

**A/S 쪽에서 무엇이 지워질지 미리 보려면 이것을 돌린다:**

```bash
# (NAS · 사람) 조회 전용 — 한 글자도 안 지운다
sh /volume1/dss/setup/trash-status.sh
```

「기한지남」 칸이 **그날 밤 지워질 건수**다. 0 이 아니면 그만큼 지워졌어야 할
것이 남아 있다는 뜻이고, 그날 밤 03:30 에 그것이 사라진다.

### 🔴 포털 쪽은 반대다 — `--dry-run` 이 있다

`purge-expired.ts` 는 `--dry-run` 을 받는다(그 파일 33줄
`process.argv.includes("--dry-run")`, 2026-10-25 실측). **위 문단을 포털에도
그대로 믿으면 안 된다.** 붙이면 표마다 몇 건을 지울 수 있는지 **세기만 하고
한 건도 안 지운다.**

🔵 **그래도 야간 작업에서는 붙이지 않는다.** 붙이면 그 회차가 아무것도 안
지우므로 감사 로그 3년 보관이 또 집행되지 않는다 — 넷째 회차를 더한 까닭
자체가 사라진다. 미리 보고 싶으면 **사람이 손으로** 한 번 돌린다:

```bash
# (NAS · 사람) 포털 쪽 미리보기 — --dry-run 이라 세기만 한다
/usr/local/bin/docker compose -f /volume1/dss/deploy/docker-compose.nas.yml \
  --env-file /volume1/dss/deploy/.env.nas --profile tools \
  run --rm tools-auth node --import tsx scripts/purge-expired.ts --dry-run
```

🔵 `npm run db:purge` 가 아니라 스크립트를 **직접** 부르는 까닭은 5절 맨 아래
상자에 있다(컨테이너에 `.env.local` 이 없다).
🔵 `--dry-run` 일 때 마지막 줄은 `합계 N건을 지웠습니다.` 가 아니라
`합계 N건. 실제로 지우려면 …` 이다 — **야간 작업의 집계 규칙에는 안 걸린다.**
손으로 돌린 미리보기가 그날 밤 건수로 섞여 들어갈 일이 없다는 뜻이다.

## 3. 왜 03:30 인가 — 백업 뒤여야 한다

**이 작업은 되돌릴 수 없다.** 휴지통으로 옮기는 것이 아니라 `DELETE` 다.
잘못 지워진 것을 되살릴 길은 **그날 백업뿐**이다. 그래서 둘을 건다.

1. **백업 02:30 → 완전삭제 03:30.** 지우기 전의 상태가 반드시 그날 덤프에
   남는다. (인증서 갱신 03:10 과도 겹치지 않는다.)
2. **문지기 — 덤프 둘을 본다.** `purge-nightly.sh` 가 시작하자마자
   `/volume1/dss/backups/db/` 에서 **오늘 날짜의 덤프 두 개**를 찾는다:
   `dss_as_<오늘날짜>_*.dump`(ㄱ 세 회차의 근거)와
   `dss_auth_<오늘날짜>_*.dump`(ㄴ 포털 회차의 근거).
   둘 다 야간 백업이 이미 뜨고 있어 **이름 모양이 같다**
   (`backup-nightly.sh` 의 `dump dss-pg-auth dss_auth_app dss_auth`).
   🔵 이름이 `.part` 를 떼고 제 이름을 받았다는 것 자체가 「`pg_restore -l`
   로 열리는 덤프가 오늘 남았다」는 뜻이다. 그래도 빈 파일인지 한 번 더 본다.

야간 백업이 조용히 죽어 있는 채로 며칠이 지나면(이남준 님 PC 에서 2주간
실제로 일어난 일 — `backup-nightly.sh` 머리말) 안전망 없이 영구 삭제만 계속
도는 셈이 된다. 문지기는 그 상황을 막는다.

### 🔴 두 문지기를 한 덩어리로 묶지 않았다

묶으면 포털 덤프 하나가 없는 날 **A/S 셋까지 멈춘다** — 2026-09-29 부터 제
일을 하고 있는 것을 세우는 쪽이 손해다. 반대도 같다. 그래서 갈래가 둘이다.

| 오늘 덤프 | A/S 세 회차 | 포털 회차 | 종료 코드 |
|---|---|---|---|
| 둘 다 있다 | 돈다 | 돈다 | `0` (실패가 없으면) |
| 🔴 `dss_as` 가 없다 | **안 돈다** | 안 돈다 | `2` — 한 건도 안 지우고 멈춘다 |
| `dss_as` 는 있고 `dss_auth` 만 없다(또는 0바이트) | **그대로 다 돈다** | 건너뛴다 | `1` — 사람이 봐야 한다 |

세 번째 줄이 중요하다. **건너뛴 그 밤에는 감사 로그 3년 보관이 집행되지
않는다.** 로그에 까닭과 할 일이 찍히고(5절 둘째 예시), 종료 코드 1 이라 DSM
이 「비정상 종료」로 표시해 메일이 온다. 🔵 포털 쪽은 **하루 밀려도 지장이
없다** — 3년 보관에서 하루는 의미가 없고, 다음 날 밤에 함께 걷힌다.

## 4. 파일을 NAS 로 올린다

올리는 법은 06·08 과 같다 — `setup/incoming/` 에 두고 사람이 `sudo` 로 옮긴다.

```powershell
# (개발 PC · PowerShell) — scp 는 -O 를 붙인다. 없으면 DSM 에 sftp 가 없어 실패한다
cd C:\Users\희만\Desktop\Development\dss-deploy
scp -O nas\jobs\purge-nightly.sh dss-nas:/volume1/dss/setup/incoming/purge-nightly.sh
```

```bash
# (NAS · 사람 · sudo -i) — 다른 jobs/ 파일과 같은 권한으로 옮긴다
mv /volume1/dss/setup/incoming/purge-nightly.sh /volume1/dss/jobs/purge-nightly.sh
chown root:root /volume1/dss/jobs/purge-nightly.sh
chmod 700       /volume1/dss/jobs/purge-nightly.sh

# 제대로 갔는지 — 옆 파일들과 같은 모양이어야 한다
ls -l /volume1/dss/jobs/
bash -n /volume1/dss/jobs/purge-nightly.sh && echo "문법 OK"
md5sum /volume1/dss/jobs/purge-nightly.sh
```

```powershell
# (개발 PC · PowerShell) 같은 값이 나오는지 대조한다
Get-FileHash -Algorithm MD5 nas\jobs\purge-nightly.sh
```

> ⚠️ **`chmod 700` · `chown root:root` 를 빠뜨리지 마라.** root 가 매일 밤
> 실행하는 파일을 관리자 계정이 고칠 수 있으면, 그 파일이 곧 root 권한의
> 뒷문이 된다(`03-install-backup.sh` 와 같은 이유).

## 5. 🔴 올린 뒤 손으로 한 번 돌린다

**스케줄러에 맡기고 다음 날 아침까지 기다리지 마라.** 올린 그 자리에서 한 번
돌려 **넷째 회차가 실제로 붙었는지** 본다. (2026-09-29 첫 등록 때도 같은
순서였다. 그때는 A/S 대상이 0건이라 가장 안전한 날이었다.)

```bash
# (NAS · 사람 · sudo -i)
bash /volume1/dss/jobs/purge-nightly.sh ; echo "종료 코드 $?"
```

> 🔵 **아래 두 예시는 2026-10-25 모래상자 실측이다.** 가짜 `docker` 를 물려
> `purge-nightly.sh` 를 끝까지 돌려 받은 출력 그대로다. 경로만 모래상자의
> `/tmp/purgetest` 를 운영의 `/volume1/dss` 로 되돌렸다(스크립트의 `D` 변수
> 하나다). A/S 세 회차의 속줄(`eligible:` …)은 **가짜 도구가 낸 것**이라
> 운영에서는 더 길다 — 🔴 **거기 말고 `✓`/`✗` 줄과 맨 아래 두 줄을 대조하라.**

### 예시 ① 네 회차가 다 돈 밤 (종료 코드 0)

```
DSS 야간 정리 · A/S 휴지통 완전삭제 + 포털 만료행 · 2026-10-25 00:02:51

── 문지기 · 오늘(2026-10-25) 백업 확인
  ✓ dss_as_2026-10-25_0230.dump · 1.0K
  ✓ dss_auth_2026-10-25_0230.dump · 1.0K

── 수리 건
  eligible: 0
  purged: 0
  skipped: 0
  errored: 0
  ✓ 수리 건 · 지움 0 건

── 진단 순서도
  ✓ 진단 순서도 · 지움 0 건

── 기준정보 · PO(내자·견적서)
  ✓ 기준정보 · PO(내자·견적서) · 지움 0 건

── 포털 · 다 쓴 행 정리 (감사 로그 3년 포함)

다 쓴 행 정리

  authorization_codes           12건 지웠습니다  (만료 후 7일)
  access_tokens                  8건 지웠습니다  (만료 후 7일)
  sso_sessions                   3건 지웠습니다  (만료·폐기 후 30일)
  audit_logs                    14건 지웠습니다  (3년)
  notification_dismissals        0건 지웠습니다  (지운 뒤 하루)

  합계 37건을 지웠습니다.

  ✓ 포털 · 지움 37 건

── 합계 · 영구 삭제 0 건 · 개별 오류 0 건 · 포털 만료행 37 건
── 성공 · 2초
종료 코드 0
```

🔵 **포털의 37건은 가짜 도구가 낸 숫자다** — 「합계 N건을 지웠습니다.」에서
N 을 뽑는 규칙이 실제로 먹는지 보려고 일부러 0 이 아닌 값을 냈다. 지울 것이
없는 밤에는 포털 자리가 이렇게 끝난다(이것도 같은 날 모래상자 실측):

```
  정리할 것이 없습니다.

  ✓ 포털 · 지움 0 건
```

> 🔴 **운영 첫 밤에는 포털 쪽이 0건이 아닐 가능성이 높다.** A/S 휴지통과
> 달리 포털은 2026-09-14 부터 돌아 **만료된 인가 코드·액세스 토큰·SSO 세션이
> 이미 쌓여 있다.** 그 숫자가 크게 찍혀도 고장이 아니다 — 한 번도 걷은 적이
> 없던 것을 처음 걷는 것이다. 🔵 다만 `audit_logs` 는 **0 이어야 한다.**
> 이 시스템이 생긴 지 3년이 안 됐다. 거기에 0 이 아닌 숫자가 찍히면 멈추고
> 알려라 — 보관 기간 계산이 틀렸다는 뜻이다.

### 예시 ② `dss_auth` 덤프가 없어 포털만 건너뛴 밤 (종료 코드 1)

```
── 문지기 · 오늘(2026-10-25) 백업 확인
  ✓ dss_as_2026-10-25_0230.dump · 1.0K
  ✗ 오늘 날짜의 dss_auth 덤프가 /volume1/dss/backups/db 에 없다 — **포털 회차만** 건너뛴다.
    (A/S 셋은 그대로 돈다. 아래 포털 자리와 종료 코드를 볼 것)

   …(A/S 세 회차는 그대로 다 돈다 — ✓ 줄 셋)…

── 포털 · 다 쓴 행 정리 (감사 로그 3년 포함)
  🔴 건너뜀 — 오늘(2026-10-25) dss_auth 덤프가 없다(위 문지기 참고).
     포털 정리도 되돌릴 수 없는 DELETE 라, 그날 백업 없이는 돌리지
     않는다. 즉 **감사 로그 3년 보관이 오늘 밤에는 집행되지 않았다.**
     A/S 셋은 그대로 다 돌렸다.

     할 일:  bash /volume1/dss/jobs/backup-nightly.sh   (왜 안 떴는지도 함께 본다)
             bash /volume1/dss/jobs/purge-nightly.sh    그 뒤 이 작업을 다시
     🔵 하루 밀려도 지장은 없다 — 다음 날 밤에 함께 걷힌다.

── 합계 · 영구 삭제 0 건 · 개별 오류 0 건 · 포털 만료행 건너뜀
── 실패가 있다 ( purge-expired=건너뜀) · 2초 — 위 ✗ 줄을 볼 것
   건너뛴 회차 말고는 그래도 전부 돌렸다. 같은 줄이 며칠 반복되면
   사람이 손봐야 한다는 뜻이다.
```

기록은 `/volume1/dss/setup/logs/purge-<날짜>_<시각>.log` 에 남는다.

**종료 코드로 읽는 법**

| 코드 | 뜻 | 할 일 |
|---|---|---|
| `0` | **네 회차 다 정상** (A/S 셋 + 포털 하나) | 다음 절로 |
| `1` | 하나 이상 실패했거나 🔴 **포털 회차를 건너뛰었다** (**나머지는 그래도 다 돌렸다**) | 로그의 `✗` 줄을 본다. 맨 아래 `실패가 있다 (…)` 괄호에 무엇이 걸렸는지 적힌다 — 아래 표 |
| `2` | 🔴 **문지기가 막았다 — 아무것도 지우지 않았다** | 오늘 `dss_as` 덤프가 없다는 뜻이다. 아래 참조 |

종료 코드 1 일 때 괄호 안에 찍히는 꼬리표:

| 꼬리표 | 뜻 |
|---|---|
| `purge:repair-cases=<N>` 등 | A/S 그 회차가 종료 코드 N 으로 죽었다 |
| `purge-expired=<N>` | 포털 회차가 종료 코드 N 으로 죽었다(DB 에 못 붙었거나 쿼리가 터졌다) |
| `purge-expired=건너뜀` | 오늘 `dss_auth` 덤프가 없어 **돌리지 않았다**(예시 ②) |
| 🔴 `purge-expired=출력형식` | **돌긴 돌았는데 건수를 셀 수 없었다.** 포털이 마무리 줄(`합계 …` / `정리할 것이 없습니다.`)을 안 찍었다는 뜻이다 — 저쪽 문구가 바뀌었을 수 있다. 🔴 **그 밤의 「지움 0건」을 믿지 마라.** 실제로는 지워졌을 수 있다. 로그를 그대로 Claude 에게 준다 |

> 🔵 **왜 포털만 `npm run` 을 안 쓰나.** `dss-auth/package.json` 의 `db:purge`
> 는 `node --env-file=.env.local --import tsx scripts/purge-expired.ts` 인데
> **컨테이너에는 `.env.local` 이 없어 그 줄에서 바로 죽는다.** 컨테이너에는
> `DATABASE_URL` 이 compose 로 이미 들어와 있으므로 파일 없이 스크립트를 직접
> 부른다(`run --rm tools-auth node --import tsx scripts/purge-expired.ts`).
> 그 저장소 `Dockerfile` 의 `tools` 스테이지 주석에 같은 우회법이 적혀 있고,
> 거기서 `scripts/` 를 일부러 담는다.

종료 코드 2 가 나오면 **그것도 정상 동작이다**(예: 02:30 전에 돌렸다).
화면이 시키는 대로 하면 된다:

```bash
# (NAS · 사람 · sudo -i)
tail -30 /volume1/dss/setup/logs/backup-*.log | tail -40   # 왜 백업이 없나
bash /volume1/dss/jobs/backup-nightly.sh                   # 손으로 한 번
bash /volume1/dss/jobs/purge-nightly.sh                    # 그 뒤 다시
```

**제어판 → 작업 스케줄러 → 생성 → 예약된 작업 → 사용자 정의 스크립트**

## 7. 🔴 등록한 뒤 목록에 실제로 보이는지 확인한다

> **만든 것과 도는 것은 다르다.**
> 2026-09-29 당시, 야간 백업에서 「저장소에는 고쳤는데 NAS 에 안 올렸다」가
> **11일간 드러나지 않았다.** 등록했다고 믿고 넘어가면 같은 일이 또 난다.
> 🔴 **2026-10-25 의 넷째 회차가 바로 그 상태다** — 커밋은 됐고 NAS 에는
> 아직 안 올라갔다. 그러니 4절 뒤에 아래 3·4번을 **한 번 더** 한다.

등록 직후 **눈으로** 확인할 것:

1. **작업 스케줄러 목록에 `DSS Purge` 줄이 실제로 보이는가.**
   「사용」 칸에 체크가 들어가 있는가(만들고 활성화를 안 하는 실수가 흔하다).
2. 그 줄을 골라 **[실행]** 을 한 번 눌러 본다 → **[작업] → [결과 보기]** 로
   종료 상태가 정상인지 본다.
3. NAS 에 기록이 남았는지 본다:

```bash
# (NAS · 사람)
ls -lt /volume1/dss/setup/logs/purge-*.log | head -3
```

4. **다음 날 아침 한 번 더 본다.** 그날 03:30 자 로그가 있어야 한다:

```bash
# (NAS · 사람)
cat /volume1/dss/setup/logs/purge-$(date +%F)_03*.log
```

`── 합계 · 영구 삭제 N 건` 줄이 그날 밤 **A/S 휴지통에서** 사라진 건수다.
🔵 그 뒤에 `· 포털 만료행 N 건` 이 따로 붙는다 — **성질이 달라 일부러 합치지
않았다**(8절의 「기한지남」 대조가 A/S 쪽 숫자여야 하기 때문이다).
`· 포털 만료행 건너뜀` 이면 그 밤에는 포털 회차가 안 돈 것이다(3절 표).

🔴 **넷째 회차가 실제로 붙었는지는 이 한 줄로 본다:**

```bash
# (NAS · 사람) 가장 최근 로그에 포털 자리가 있는가 — 하루에 여러 번 돌려도
# 한 파일만 보도록 ls -1t | head -1 로 고른다
grep -c "── 포털" "$(ls -1t /volume1/dss/setup/logs/purge-*.log | head -1)"
```

**1 이어야 한다.** 0 이면 옛 파일이 그대로 돌고 있다는 뜻이다 — 4절을 다시
한다. 🔵 「올렸다고 생각한 것」과 「올라간 것」은 다른 일이다(4절 md5 대조).

## 8. 그 뒤 — 무엇을 정기적으로 보나

| 언제 | 무엇 | 어떻게 |
|---|---|---|
| 등록 다음 날 | 03:30 에 실제로 돌았나 | 위 7절 4번 |
| 🔴 넷째 회차를 올린 다음 날 | 포털 자리가 로그에 있나 | 위 7절 4번의 `grep -c "── 포털"` 이 **1** |
| 처음으로 실제 삭제가 일어나는 날 | 지워진 건수가 맞나 | 전날 `trash-status.sh` 의 「기한지남」 = 그날 로그의 「영구 삭제 N 건」. 🔵 **「포털 만료행 N 건」은 이 대조에 넣지 않는다** — `trash-status.sh` 는 A/S 휴지통만 센다 |
| 매월 | 실패가 반복되지 않나 | `grep -l "실패가 있다" /volume1/dss/setup/logs/purge-*.log` |
| 🔴 매월 | 포털 회차가 조용히 안 돌고 있지 않나 | `grep -l "포털 만료행 건너뜀" /volume1/dss/setup/logs/purge-*.log` — 며칠씩 이어지면 `dss_auth` 백업이 죽은 것이다 |

`skipped (referenced by repair cases)` 가 **0이 아닌 채로 매일 밤 반복**되면
사람이 손봐야 한다는 신호다 — 휴지통에 들어간 뒤 접수 건이 걸린 고객사가
있다는 뜻이고, 손대기 전까지 그 행은 영원히 지워지지 않는다
(`purge-expired-master-data.ts` 주석).

기록은 **개수로** 정리한다 — 최근 60개(두 달치)만 남는다. 작업이 몇 주 멈춰도
마지막 기록들은 지워지지 않는다(야간 백업·교정 알림과 같은 규칙).

## 9. 되돌리기

**없다.** 영구 삭제는 되돌릴 수 없다. 길은 둘뿐이다.

1. **그날 백업에서 복원한다** — A/S 세 회차는
   `/volume1/dss/backups/db/dss_as_<날짜>_*.dump`, **포털 회차는
   `dss_auth_<날짜>_*.dump`** 다. 문지기가 **그 회차의 덤프**가 있는 것을
   확인한 뒤에만 지웠으므로, 지우기 직전 상태는 반드시 남아 있다.
2. **작업을 멈춘다** — DSM 작업 스케줄러에서 `DSS Purge` 의 「사용」 체크를
   끈다. 파일을 지울 필요는 없다.
