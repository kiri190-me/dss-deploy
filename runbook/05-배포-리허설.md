# 05 — 배포 리허설

> **결정 B가 약속한 문서다.** 상시 staging 을 NAS 에 두지 않는 대신 이것을 한다.
> 그 문서가 없는 동안 결정 B 는 사실상 「staging 을 안 만들었다」였다(README 가 스스로
> 그렇게 적어 두었다). 이 문서가 그 자리를 채운다.
>
> 작성 2026-09-07. **아직 한 번도 끝까지 해 보지 않았다** — 절차이지 기록이 아니다.
> 처음 해 보고 나면 실제로 걸린 것들을 여기에 되먹인다.

---

> **2026-09-14 — 이 문서의 절반을 NAS 에서 실제로 했다.** G3(컨테이너 예행)는 개발 PC 대신 **NAS 예행**
> (`nas/setup/02-rehearse.sh`)으로 했고 브라우저 확인까지 통과했다. 11절 구멍 ㄱ·ㄷ 은 메웠다. 남은 것:
> 도구 이미지(6절) · G4 마이그레이션 리허설 · 11-ㄴ · G3 11번(20MB 엑셀 메모리)·12번(재기동 시간).
> **이 문서가 적은 새 이미지 배포 절차(G5·G6)는 아직 한 번도 하지 않았다.**
## 0. 이 문서가 답하는 질문

> **"사람들이 쓰고 있는 서비스에 내가 새 기능을 바로 꽂게 되는 것이냐."**

아니다. 지금 구조에서 개발 PC 의 코드가 NAS 의 서비스에 닿으려면 **사람이 손으로 하는
단계를 넷** 지나야 한다(런북 02 4절). `git push` 를 해도 NAS 는 그쪽을 보지 않는다.

그런데 안전한 것은 **이미지**뿐이다. 이미지는 태그를 되돌리면 1분이면 돌아온다.
**마이그레이션은 돌아오지 않는다.** 이 문서에 적힌 절차 전체의 목적은 하나다 —

> **되돌릴 수 없는 상태에 빠지는 경우를 만들지 않는다.**

9절의 되돌리기 표에서 **「라」 줄이 생기지 않게 하는 것**, 그것뿐이다.

### 「리허설」이 이 저장소에서 세 가지를 가리킨다

혼동을 막기 위해 여기서 다시 못박는다.

| | 무엇 | 어디 | 상태 |
|---|---|---|---|
| 2단계 리허설 | NAS 와 **같은 모양의 DB** 를 개발 PC 에 먼저 세워 본 것 | 런북 01 | ✅ 2026-09-03 |
| **배포 리허설** | **배포 절차 전체를 한 번 예행** — 결정 B 가 택한 것 | **이 문서** | ⬜ 아직 |
| `nas/docker-compose.rehearsal.yml` | 개발 PC 에서 NAS 의 **DB 둘만** 띄우는 compose | `nas/` | 매일 쓴다 |

이 문서가 새로 제안하는 `docker-compose.smoke.yml`(4절)은 **넷째가 아니다** —
배포 리허설의 한 관문(G3)을 실행하는 도구이고, 그래서 이름을 「리허설」로 짓지 않았다.

## 1. 관문 지도

```
 [G0 아침]  npm run work:start
     │
 [G1 코드]  tsc · lint · test · test:db · build          ← 명령이 이미 다 있다
     │
 [G2 이미지] docker build (운영 + 도구, 같은 태그)         ← 태그 규칙만 새로
     │
 [G3 컨테이너 예행] 개발 PC 에서 운영 이미지를 띄운다      ← ★ 지금 완전히 비어 있다
     │
 [G4 마이그레이션 리허설] 진짜 자료 사본에 먼저 돌린다      ← 결정 B 의 본문
     │
 ══════════ 여기까지 NAS 없이 전부 가능 ══════════
     │
 [G5 운반]  save → 복사 → load
     │
 [G6 적용]  저녁 정지 창 (목표 10분)
     │
 [G7 관측]  다음 날 아침까지
```

**G1~G4 는 NAS RAM 을 기다릴 필요가 없다.** 그중 G1 은 이미 완성돼 있고,
G3·G4 가 비어 있는 자리다.

## 2. G1 — 코드 관문 (개발 PC)

| | |
|---|---|
| **검증** | 타입 · 린트 · 단위 · 컴포넌트 · DB 통합 · 프로덕션 빌드 |
| **통과** | 여섯 개 전부 종료 코드 0 |
| **실패** | 여기서 고친다. G2 로 넘어가지 않는다 |

```bash
cd "C:/Users/희만/Desktop/Development/RF_Service_System"
npx tsc --noEmit
npm run lint
npm test
npm run test:components
npm run test:db          # pretest:db 훅이 안전장치 + 시험 DB 준비를 먼저 돈다
npm run build
```

**순서에 이유가 있다.** `tsc` 가 가장 싸고 가장 넓게 잡는다.
**`build` 를 반드시 넣는다** — `next dev` 는 통과하는데 `next build` 만 죽는 종류가
이 저장소에서 실제로 있었다(런북 02 7절 ①). G3 에서 그것을 만나면 도커 로그 안에서
만나게 되어 훨씬 읽기 어렵다.

⚠️ **`npx tsc --noEmit` 은 `.next/` 가 없으면 통과한 것처럼 보인다.**
생성된 route 타입을 `.next/types/` 가 갖고 있기 때문이다. 기준선을 잴 때 속기 쉬운
자리다(`RF_Service_System/HANDOFF.md` 의 1-1 항목). `build` 를 마지막에 두면 이 함정도
같이 닫힌다.

**이 관문에 새로 만들 것은 없다.** 명령이 전부 이미 있다.

## 3. G2 — 이미지 관문

```bash
# 운영 이미지
docker build -t dss-as:1.1 .

# 도구 이미지 — 6절에서 정한 길 ㄴ
docker build --target tools -t dss-as-tools:1 .
```

통과 기준 넷:

```bash
docker run --rm dss-as:1.1 pg_dump --version          # → 17.x
docker run --rm dss-as:1.1 ls public/theme-init.js    # 있어야 한다
docker run --rm dss-as:1.1 ls .next/static            # 비어 있으면 안 된다
docker run --rm -e TZ=Asia/Seoul dss-as:1.1 date      # → KST
```

**`public/theme-init.js` 를 따로 확인하는 이유** — `src/app/layout.tsx` 가 **런타임에**
이 파일을 읽는다. 빠지면 CSS 만 깨지는 것이 아니라 첫 화면부터 죽는다.
Dockerfile 주석에 이미 적혀 있는 함정이다.

**`date` 를 확인하는 이유** — 컨테이너 기본 시간대는 UTC 다. 업무 로직은
`Asia/Seoul` 을 못박아 안전하지만(`src/lib/domain/date-only.ts`), 표시용
`toLocaleString("ko-KR")` 이 시간대 없이 여러 군데 쓰인다. 서버가 UTC 면 화면에
찍히는 시각이 9시간 어긋난다.
⚠️ `node:22-bookworm-slim` 에 tzdata 가 들어 있는지 **확인하지 못했다.** UTC 로
나오면 Dockerfile 에 `apt-get install -y tzdata` 를 더한다.

### 태그 규칙

- `dss-as:1.1`, `1.2`, `1.3` … 배포마다 하나씩 올린다.
- **`latest` 를 만들지 않는다.** 무엇이 돌고 있는지 알 수 없게 된다(런북 02 5절).
- **옛 태그를 지우지 않는다.** 되돌리기가 태그 하나인 것은 옛 이미지가 남아 있을
  때만 성립한다.
- 어느 태그가 언제 나갔는지는 **`RF_Service_System/CHANGELOG.md`** 에 한 줄로 남긴다.
  새 원장을 만들면 갈라진다.

### 제안 — 이미지가 자기 버전을 답하게 한다

지금은 **돌고 있는 컨테이너에게 "너는 몇 번이냐"고 물을 방법이 없다.**
compose 의 `image:` 줄을 사람이 읽는 것이 유일한 길인데, 그것은 "compose 가 실제로
적용됐다"는 가정 위에 서 있다. `up -d` 를 빠뜨린 채 태그만 고쳐 둔 상태가 정확히
가장 헷갈리는 상태다.

Dockerfile 에 세 줄이면 이 질문이 영구히 닫힌다 — `ARG APP_VERSION` / `GIT_SHA` →
`LABEL` + `ENV NEXT_PUBLIC_APP_VERSION`.

## 4. G3 — 컨테이너 예행 ★

> **이 프로젝트에서 앱은 아직 컨테이너로 돌아 본 적이 없다.**
> 이미지는 굽고 `save`/`load` 왕복까지 했지만(3단계) 띄워 본 것은 아니다.
> 그 첫 시도를 **운영 장비에서 하지 않는 것**이 이 관문의 전부다.

「처음 해 보는 일을 운영 장비에서 처음 하지 않는다」 — README 가 2단계를 먼저 둔
이유와 같다. 그리고 이 관문은 **NAS 자원을 한 톨도 쓰지 않는다. RAM 을 기다릴 필요가
없다.**

### 4-1. 새로 만들 파일 — `RF_Service_System/docker-compose.smoke.yml`

🔴 **아직 없다. 만들어야 한다.**

| 후보 | 판단 |
|---|---|
| 기존 `docker-compose.yml` 에 app 서비스 추가 | ❌ 그 파일은 은퇴했다 — `start-work.ps1` 이 더 이상 그 `db-dev` 를 켜지 않고, 볼륨은 Phase 7 회수 대상이다 |
| `profiles` 로 그 파일 안에 | ❌ 같은 이유. `profiles: [staging]` 이 이미 있어 "안 뜨는 서비스"가 둘이 된다 |
| `dss-deploy` 에 둔다 | ❌ CLAUDE.md — "Dockerfile 은 각 저장소에". 한 앱의 이미지를 혼자 띄워 보는 일은 네 시스템을 잇는 일이 아니다 |
| **A/S 저장소에 새 파일** | ✅ 이미지가 그 저장소 것이므로 검증하는 자리도 거기다 |

**이름을 `docker-compose.rehearsal.yml` 로 하지 않는다** — `nas/` 에 같은 이름이 이미
있고, 「리허설」이 무엇을 가리키는지 이 저장소가 이미 한 번 정리했다(0절).

핵심만 적으면:

```yaml
name: dss-as-smoke              # dss 프로젝트를 건드리지 않도록 이름을 가른다

networks:
  dss-data: { name: dss_dss-data, external: true }   # DB 가 있는 내부망
  dss-edge: { name: dss_dss-edge, external: true }   # SMTP·SSO 가 나가는 길

services:
  app-smoke:
    image: dss-as:${AS_IMAGE_TAG:?태그를 지정하세요 (예: 1.1)}
    networks: [dss-data, dss-edge]
    ports: ["3000:3000"]
    environment:
      TZ: Asia/Seoul
      UPLOADS_DIR: /data
      DATABASE_URL: postgresql://dss_app:...@dss-pg-app:5432/dss_as_rehearsal
    volumes:
      - C:\DSS-AS-DATA\uploads:/data
      - C:\DSS-AS-DATA\templates:/templates:ro
    deploy: { resources: { limits: { memory: 640M } } }
```

두 가지가 일부러 이렇게 돼 있다.

- **`dss-edge` 를 붙인다.** `dss-data` 는 `internal: true` 라 그 망만 가진 컨테이너는
  바깥으로 못 나간다. 접수 알림 메일(SMTP)·dss-home 동기화·SSO 토큰 교환이 전부 바깥으로
  나가는 요청이다. NAS 의 `app-as` 도 두 망을 다 갖고 있으므로 **모양이 같다.**
- **3000 을 쓰고 `next dev` 를 끈다.** 3010 으로 피하면 포털에 등록된 `redirect_uri` 와
  글자가 어긋나 로그인이 막힌다 — 포털은 와일드카드도 정규화도 하지 않는다.

⚠️ **견본을 `.env.smoke.example` 로 만들지 말 것.** `.gitignore` 가 `.env*` 를 통째로
막고 예외는 `!.env.example` 하나뿐이라 **조용히 커밋되지 않는다.** 견본은
compose 파일 머리 주석에 넣는다(파일이 하나 준다).

### 4-2. 붙일 DB — `dss_as_rehearsal`

같은 `dss-pg-app` 인스턴스 안에 DB 를 하나 더 만든다. 새 컨테이너를 세우지 않는다 —
비용이 0 이고 `dss_as_test` 로 이미 그 패턴이 서 있다.

```sql
-- ⚠️ ICU 로케일을 운영과 같게 준다. 다르면 ORDER BY 결과가 달라져
--    리허설이 아무것도 증명하지 못한다.
CREATE DATABASE dss_as_rehearsal
  OWNER dss_app ENCODING 'UTF8'
  LOCALE_PROVIDER icu ICU_LOCALE 'ko-KR' LOCALE 'C.UTF-8' TEMPLATE template0;

-- init/app/01-roles.sh 가 PUBLIC 의 CONNECT 를 걷어냈으므로 새 DB 도 같이 잠근다
REVOKE CONNECT ON DATABASE dss_as_rehearsal FROM PUBLIC;
GRANT  CONNECT ON DATABASE dss_as_rehearsal TO dss_app;
```

무엇을 복원하나 — **시기에 따라 다르다.**

| 시기 | 넣는 것 |
|---|---|
| 지금 (운영 DB 없음) | `C:\DSS-AS-DATA\backups\postgres` 의 최신 `end-work.ps1` 덤프 |
| NAS 가 선 뒤 | **운영 `dss_as` 의 덤프.** 이것이 결정 B 의 본문이다 |

### 4-3. 호스트 경로 의존 — 넷으로 갈린다

| 값 | 누가 읽나 | 컨테이너에서 |
|---|---|---|
| `UPLOADS_DIR` | **앱** (`src/lib/storage/local-fs-adapter.ts`) | `/data` — 볼륨. NAS 도 같다 |
| 양식 xlsx **6개** | **앱** (`quote-template.ts` · `service-report-template.ts`) | `/templates/…` 읽기 전용 볼륨. 🔴 **NAS compose 에 이 마운트가 없다**(11절) |
| `BACKUPS_DIR` | **도구만** (`scripts/backup-attachments.ts`) | 운영 이미지에는 필요 없다. 도구 컨테이너에만 준다 |
| `LOGS_DIR` | **아무도 안 읽는다** (`src`·`scripts` 전수 검색 결과 참조 0) | 넣지 않는다 |

🔴 **첨부 볼륨은 실제 개발 폴더를 그대로 붙인다.** 빈 폴더를 붙이면 아래 4번 항목
(기존 사진 열기)을 검증할 수 없는데, **그것이 이 관문의 핵심**이다. Windows 는 파일
이름의 대소문자를 구분하지 않아 개발 중에는 절대 드러나지 않고 Linux 에서 처음
드러난다. **스모크는 `npm run work:end` 백업 직후에 돌린다.**

### 4-4. 통과 기준 — 열두 가지

| | 확인 | 왜 이것인가 |
|---|---|---|
| 1 | 기동 — 로그에 `Ready in`, 예외 없음 | — |
| 2 | 첫 화면 — 테마 깜빡임 없음, CSS·아이콘 정상 | `theme-init.js` 와 `.next/static` 이 담겼는가 |
| 3 | **로그인 (SSO 왕복)** — `iss`·`redirect_uri` 가 컨테이너 IP 가 아님 | README 가 경고한 **7단계 지뢰**(`auto`·`{lan}` 이 컨테이너 IP 를 읽는다)를 여기서 미리 밟는다 |
| 4 | **기존 사진 10장 이상 실제로 연다** | 하나라도 404 면 대소문자 또는 경로 구분자. **Windows 에서는 절대 안 나오는 실패** |
| 5 | 새 업로드 1장 — 호스트에서 파일이 생겼는지 눈으로 확인 | `attachment-path.ts` 의 규칙 셋(슬래시·소문자·상대경로)이 실제 디스크에서 성립하는가 |
| 6 | `/data/.tmp-uploads` 가 생기고 업로드 후 비어 있다 | 남아 있으면 EXDEV 복사 경로를 탔다 = 마운트 구성이 갈려 있다 |
| 7 | **쓰기 권한** — `docker exec -u node … touch /data/.probe` 성공 | 컨테이너는 uid 1000 으로 돈다. NAS 에서 `chown -R 1000:1000` 이 필요한지 여기서 확정 |
| 8 | **견적서 4종 중 2종 이상 실제 출력** | 양식 파일명에 한글과 공백이 섞여 있다(`제너레이터 OH 견적서.xlsx`). Linux 에서 열리는지는 붙여 봐야 안다 |
| 9 | 검사·수리 보고서 각 1건 | 위와 같다. 양식 6개 중 하나라도 못 읽으면 그 기능이 통째로 죽는다 |
| 10 | **접수 알림 메일 1통 실제 발송** | `dss-data` 만 붙어 있으면 여기서 막힌다. **NAS 에서도 똑같이 막힌다** |
| 11 | **20MB 엑셀 파싱 중 `docker stats` 최대치 + `OOMKilled` 확인** | **640M 상한이 한 번도 실측된 적이 없다.** NAS 예산 2.7GB 전체가 이 숫자 위에 서 있다 |
| 12 | `down` → `up -d` 후 자료 그대로 · **기동 시간 측정** | G6 정지 창 예산의 근거 |

> **개발 PC 에서 잰 것 중 옮겨 적어도 되는 것과 아닌 것** —
> **메모리 최대치는 옮겨도 된다**(cgroup 이 같은 방식으로 건다).
> **시간은 옮기지 않는다** — DS218+ 는 Celeron 2코어에 HDD 다. 기동·마이그레이션
> 시간은 5단계에서 다시 잰다.

### 4-5. 이 관문의 진짜 산출물

걸리는 것은 **대부분 코드가 아니라 설정**이다. 고친 것을 반드시
`nas/env/as.env` 초안과 `nas/docker-compose.nas.yml` 에 **되먹인다.**
그 되먹임이 G3 의 산출물이다 — 11절의 「양식 볼륨이 빠졌다」가 정확히 이 방식으로
잡히는 종류다.

⚠️ **확신 없음** — Docker Desktop(Windows) 컨테이너에서 호스트의 LAN IP 로
`dss-auth:3100` 에 닿는지 실측하지 않았다. 안 되면 항목 3을
`extra_hosts: host.docker.internal:host-gateway` 로 우회하거나, 1차는
`LOGIN_MODE=demo` 로 기동만 확인하고 SSO 는 2차로 미룬다.

## 5. G4 — 마이그레이션 리허설

| | |
|---|---|
| **검증** | 진짜 자료가 든 DB 에서 도는가 · 무엇이 사라지는가 · **옛 이미지로 돌아갈 수 있는가** · 얼마나 걸리는가 |
| **실패** | 10절의 확장-수축으로 쪼갠다. 이번 배포에서 지우는 문장을 뺀다 |

```bash
# 1. 운영에서 뜬다 (NAS 가 선 뒤)
docker exec dss-pg-app pg_dump -U dss_app -d dss_as -Fc > rehearsal.dump

# 2. 개발 PC 의 리허설 DB 에 넣는다
pg_restore -d dss_as_rehearsal --clean --if-exists rehearsal.dump

# 3. 새 마이그레이션을 진짜 자료에 돌려 본다 — 시간도 잰다
DATABASE_URL=...dss_as_rehearsal npm run db:preflight
DATABASE_URL=...dss_as_rehearsal npm run db:migrate
```

**통과 기준 셋. 마지막 것이 이 관문의 핵심이다.**

1. `db:preflight` 가 "사라지는 자료 없음" — 종료 코드 0
2. `db:migrate` 종료 코드 0, 걸린 시간 기록
3. 🔴 **옛 태그 이미지(`dss-as:1.0`)를 새 스키마에 붙여 G3 스모크를 다시 돌린다**

세 번째를 넣는 이유 — **마이그레이션이 성공하는 것과 되돌릴 수 있는 것은 다른
이야기**이고, 후자를 확인하는 자리가 지금 어디에도 없다. 9절의 「나」 줄이 실제로
성립하는지는 이렇게만 확인된다.

## 6. 컨테이너에서 스크립트를 돌리는 방법 — 길 ㄴ 으로 닫는다

> 런북 02 8절의 미결 항목. **여기서 닫는다.**

### 먼저, 매력적으로 보이던 네 번째 길이 죽었다

"운영 이미지에 `drizzle/` 폴더와 `drizzle-orm/postgres-js/migrator` 를 부르는 20줄짜리
러너만 얹으면 devDependency 없이 끝나지 않나" — `drizzle-orm` 도 `postgres` 도
**runtime dependency 라 될 줄 알았다.**

🔴 **실측하니 아니다.** `.next/standalone/node_modules` 에 있는 것은 **14개뿐**이고
(`@img` `@next` `@swc` `client-only` `detect-libc` `nanoid` `next` `picocolors`
`postcss` `react` `react-dom` `sharp` `source-map-js` `styled-jsx`) `drizzle-orm` 도
`postgres` 도 **없다.** Next 가 서버 청크에 번들해 버렸다. 이미지 안에서 부를 수 있는
모듈이 아니다.

되짚고 싶어지면 이 한 줄로 5초면 확인된다:

```bash
docker run --rm dss-as:1.1 node -e "import('drizzle-orm/postgres-js/migrator').then(m=>console.log(Object.keys(m)))"
```

### 왜 ㄱ(운영 이미지에 tsx 포함)이 아닌가

- `node_modules` 전체가 517MB. standalone 이미지에 되돌려 넣으면 `docker save` 파일이
  107MB → 300MB 대로 뛴다. **배포마다 세 배를 옮긴다.**
- 운영 이미지 안에 TypeScript 실행기와 마이그레이션 CLI 를 상주시킨다. 그 이미지는
  **파일로 복사되어 돌아다닌다** — 서명 키를 이미지에 넣지 않은 것과 같은 논리다.

### 왜 ㄷ(DSM 스케줄러가 호스트에서 docker exec) 만으로는 안 되는가

런북 02 8절은 "백업이 사진 미러링과 서명 키까지 챙기므로 부족하다"고 적었다.
**A/S 에는 거기 없는 것이 하나 더 있다.**

| 컨테이너 밖에서 돌아야 하는 일 | ㄷ 로 되나 |
|---|---|
| `db:migrate` | ❌ |
| `db:preflight` (지울 행 수 세기) | ❌ |
| `backup:attachments` (DB 대조 + 지문 검증) | ❌ |
| **`purge:repair-cases` · `purge:flowcharts` · `purge:master-data`** | ❌ |

마지막 줄이 새로 드러난 것이다. **이 셋은 일회성이 아니라 매일 밤 돌아야 하고, 지금은
Windows 의 `run-nightly-purge.ps1` 이 돌리고 있다.** NAS 로 옮기면 그 스케줄러가
사라진다. 보존기간 만료 삭제가 조용히 멈추고, 증상은 몇 달 뒤 "휴지통이 안 비워진다"로
나타난다.

`pg_dump` 만 ㄷ 로 간다 — DSM 스케줄러가 `docker exec dss-pg-app pg_dump` 를 부르는
것이 가장 싸고 앱과 무관하다.

### 채택 — ㄴ (도구 이미지). 다만 두 가지를 더한다

**① `drizzle/` 을 이미지에 굽지 말고 볼륨으로 붙인다.**
도구 이미지는 크다. 배포마다 옮기면 ㄱ 을 피한 의미가 없다. 그런데 **배포마다 바뀌는
것은 `drizzle/` 뿐이다** — 21MB, 복사로 몇 초다.

```yaml
# nas/docker-compose.nas.yml 에 더한다 — 평소엔 뜨지 않는 서비스
  tools-as:
    image: dss-as-tools:1            # 태그가 굵다. 의존성이 바뀔 때만 올린다
    profiles: [tools]                # ⚠️ up -d 로는 절대 안 뜬다. 6번째 상시 서비스로 만들지 말 것
    networks: [dss-data, dss-edge]
    env_file: [ ./env/as.env ]
    environment:
      DATABASE_URL: postgresql://dss_app:${AS_APP_PASSWORD}@dss-pg-app:5432/dss_as
      UPLOADS_DIR: /data
      BACKUPS_DIR: /backups
      TZ: Asia/Seoul
    volumes:
      - /volume1/dss/as-migrations:/app/drizzle:ro   # ← 배포마다 여기만 갈린다
      - /volume1/dss/as-attachments:/data
      - /volume1/dss/backups:/backups
      - /volume1/dss/as-templates:/templates:ro
    deploy: { resources: { limits: { memory: 512M } } }
```

```bash
docker compose -f docker-compose.nas.yml --env-file .env.nas \
  run --rm tools-as npm run db:preflight
```

`profiles:` 는 이 저장소가 이미 쓰는 관례다(`RF_Service_System/docker-compose.yml` 의
`staging`). 접속 문자열을 배포 날 밤에 손으로 다시 타이핑하지 않아도 되면서 2.7GB
예산을 건드리지 않는다.

**② 도구 이미지는 Dockerfile 의 4번째 스테이지로 만든다.**
`--target builder` 로 builder 를 그대로 쓰면 `.next` 빌드 산출물까지 딸려 온다.
`deps` 를 이어받아 `scripts/` · `src/` · `drizzle/` · 설정 파일만 담는 별도 스테이지가 낫다.

### 확인은 NAS 없이 오늘 할 수 있다

```bash
docker run --rm --network dss_dss-data \
  -e DATABASE_URL=postgresql://dss_app:…@dss-pg-app:5432/dss_as_rehearsal \
  dss-as-tools:1 npm run db:preflight
```

**이 한 줄이 성공하면 이 미결 항목은 NAS 가 서기 전에 닫힌다.**

> 확인해 둔 것 — `drizzle.config.ts` 와 `scripts/load-env.ts` 는 둘 다
> `dotenv.config({path:".env.local"})` 를 부르는데 `.dockerignore` 가 `.env*` 를 막아
> 이미지 안에 그 파일이 없다. **문제가 되지 않는다.** dotenv 는 파일이 없으면 조용히
> 지나가고 **이미 있는 `process.env` 를 덮어쓰지 않는다.** `-e DATABASE_URL=…` 이 그대로
> 산다. 코드를 고칠 필요가 없다.
>
> ⚠️ **확신 없음** — `db:preflight` 의 `DRIZZLE_DIR` 이 `process.cwd()` 기준이라
> `docker compose run` 의 working_dir 에 따라 어긋날 수 있다. 위 한 줄이 바로 그것을
> 확인하는 자리다.

### 남겨 두는 대안 (채택하지 않음)

**ㄹ — 개발 PC 가 SSH 터널로 NAS 의 DB 에 붙어 마이그레이션을 돌린다.**
이미지를 하나도 안 옮겨도 되고 매일 쓰는 명령을 글자 그대로 쓴다. 채택하지 않는
이유는 **런북 02 가 이식의 목적으로 내건 것 — "NAS 로 옮기면 개발 PC 가 운영에
관여하지 않는다" — 을 하필 자료를 부술 수 있는 그 한 작업에서 되살리기** 때문이다.
그리고 터널은 배포 날 밤에 처음 시험하는 새 물건이 되는 반면, 도구 이미지는 개발
PC 에서 미리 리허설할 수 있다.
(덧붙여, `internal: true` 망의 컨테이너에 NAS 호스트가 직접 닿는지 **확신 없다** —
되살릴 거라면 그것부터 실측해야 한다.)

## 7. G5 — 운반

```bash
# 개발 PC
docker save dss-as:1.1 -o dss-as-1.1.tar        # 107MB
docker image inspect dss-as:1.1 --format '{{.Id}}'

# NAS 공유폴더로 복사한 뒤, NAS 에서
docker load -i dss-as-1.1.tar
docker image inspect dss-as:1.1 --format '{{.Id}}'
```

**통과 기준: 두 `sha256` 이 같다.** 크기 비교로는 부족하다 — SMB 복사 중 끊김이
가장 흔한 실패다.

> ⚠️ **개발 PC 와 NAS 는 같은 이미지에 다른 숫자를 보여 준다** (2026-09-16 에 걸림).
> 개발 PC 의 Docker Desktop 은 **containerd 이미지 저장소**라 `.Id` 가 *매니페스트* 지문이고,
> NAS 의 Container Manager 24 는 고전 저장소라 *config* 지문을 ID 로 보여 준다.
> 위 두 줄을 그대로 비교하면 **멀쩡한 이미지를 놓고 틀렸다고 판단한다.**
>
> NAS 에서 맞춰 볼 값은 tar 자신이 들고 있다:
>
> ```bash
> # 개발 PC — 이 값이 NAS 의 image ID 가 된다
> tar -xzOf dss-as-1.1.tar.gz manifest.json    # .[0].Config → blobs/sha256/<지문>
> ```
>
> 저장소 방식은 `docker info | grep -i snapshotter` 로 확인한다. 내용까지 대조하려면
> 양쪽의 `docker image inspect --format {{.RootFS.Layers}}` 를 비교한다 — 이쪽은 두 저장소가
> 같은 값을 낸다.

왕복 자체는 3단계에서 이미 검증했다(실제로 이미지를 지웠다가 되살렸다).
남은 것은 배포마다 반복할 다이제스트 대조 하나뿐이다.

**도구 이미지는 매번 옮기지 않는다** — 6절 ①. 바뀌는 것은 `drizzle/` 뿐이다.

## 8. G6 — 저녁 정지 창

> **결정 (2026-09-07, 사용자)** — **무중단으로 가지 않는다. 저녁에 10분 멈춘다.**

| | 무중단(blue/green) | 저녁 정지 창 |
|---|---|---|
| 메모리 | 앱 컨테이너 둘 = +640M → 3.34GB + DSM 1.2GB = **4.5/6GB** | 그대로 |
| 전환 | **DSM 리버스 프록시 설정을 사람이 두 번 고친다** | `docker compose up -d` 한 번 |
| 스키마 제약 | 두 버전이 같은 DB 를 동시에 본다 → **확장-수축이 필수** | 확장-수축은 어차피 권장 |
| 얻는 것 | 15명이 저녁 10분을 잃지 않는다 | — |

무중단이 강제하는 제약(확장-수축)은 정지 창에서도 어차피 지킨다. **무중단이 추가로
주는 것은 저녁 10분뿐이고, 대신 전환 절차의 복잡도와 "두 버전이 동시에 도는 상태"를
산다.** 개발자 한 명, 배포 주 1회 미만, 사내 15명에서는 남는 장사가 아니다.

**창은 30분 잡고 실제 중단은 10분을 목표로 한다.** 5분은 낙관적이다 —
`docker load` + preflight + migrate + HDD 위에서의 기동 20~40초 + 3분 스모크를 더하면
그렇다. 전날 공지 한 줄이면 충분한 규모다.

### 절차

```
①  18:00 이후, 쓰는 사람이 없는 것을 확인한다 (15명이다 — 그냥 묻는다)
②  docker compose stop app-as              ← DB 는 끄지 않는다
③  docker exec dss-pg-app pg_dump -U dss_app -d dss_as -Fc \
      > /volume1/dss/backups/dss_as_<시각>.dump
④  첨부 폴더 스냅숏 —  cp -al  (하드링크, 즉시·공간 0)
⑤  docker load -i dss-as-1.1.tar
⑥  docker compose --profile tools run --rm tools-as npm run db:preflight
      └ 🔴 종료 코드 1 이면 여기서 멈춘다. 예정에 없던 삭제다
⑦  docker compose --profile tools run --rm tools-as npm run db:migrate
⑧  compose 의 image: 를 1.1 로 → docker compose up -d app-as
⑨  상태 확인 — 버전과 DB 연결
⑩  3분 스모크: 로그인 → 목록 → 사진 하나 열기 → 새 접수 1건 → 견적서 1장
⑪  통과 → 창을 닫고 공지 / 실패 → 9절 롤백
```

🔴 **③ 이 ② 뒤에 있는 이유** — 런북 01 9절 부록 1번이 실제로 겪은 것이다.
**"덤프와 전환 사이에 들어온 자료는 사라진다."** 앱을 멈춘 뒤 뜬 덤프만이 되돌릴
지점이 된다.

🔴 **④ 를 넣는 이유** — 마이그레이션은 DB 만 바꾸지만 롤백은 DB 만 되돌려서는 안
된다. `attachments` 행과 디스크 파일이 한 쌍이라야 쓸모가 있다
(`end-work.ps1` 2.1절이 같은 논리를 이미 적어 두었다).

## 9. 되돌리기

| | 상황 | 되돌리는 것 | 잃는 것 | 시간 |
|---|---|---|---|---|
| **가** | 코드만 (마이그레이션 없음) | 이미지 태그 → `up -d` | 없음 | 1분 |
| **나** | 마이그레이션이 **더하기만** | 이미지 태그만. **DB 는 그대로 둔다** — 옛 코드는 새 열을 무시한다 | 없음 | 1분 |
| **다** | 되돌릴 수 없는 구문 · **정지 창 안** | `stop` → `dropdb`/`createdb` → ③ 덤프 복원 → ④ 스냅숏 되돌림 → 태그 | **없음** (아무도 안 썼다) | 10~20분 |
| **라** | 되돌릴 수 없는 구문 · **다음 날 발견** | **사실상 불가** | 하루치 전부 | — |

**설계의 전부는 「라」 줄이 존재하지 않게 만드는 것이다.** 방법은 셋뿐이다.

1. **10절 확장-수축** — 되돌릴 수 없는 것을 배포에 섞지 않는다.
2. **11절 도구 확장** — 섞였는지 사람이 아니라 도구가 본다.
3. 🔴 **되돌리기 결정 시한을 정지 창 안으로 못박는다.** ⑩ 3분 스모크를 통과하지
   못하면 **무조건** 되돌린다. **"조금만 더 보면 될 것 같다"가 가장 비싼 판단이다** —
   그렇게 창을 넘기면 「다」가 「라」로 바뀐다.

표 하나가 문제일 때의 중간 길도 있다. preflight 가 이미 그 명령을 안내한다:
`docker exec dss-pg-app pg_dump -U dss_app -d dss_as -t <표이름>` → 그 표만 되돌린다.

## 10. 마이그레이션은 셋으로 쪼갠다 (확장 → 채우기 → 수축)

| 릴리스 | 하는 일 | 되돌리기 |
|---|---|---|
| N | `ADD COLUMN … NULL` (기본값도 NOT NULL 도 없이). 새 코드가 새 열에 쓰고, 읽을 때 없으면 옛 열 | **태그 하나.** 옛 코드는 새 열을 그냥 무시한다 |
| N+1 (한 주 뒤) | 채우기 스크립트 → `SET NOT NULL` | 태그 하나. **단, 여기서부터 옛 코드가 깨진다** |
| N+2 | `DROP COLUMN` | 불가. preflight 가 여기서 처음 경고를 낸다. **그때만 사람이 승인한다** |

**이름은 바꾸지 않는다.** `RENAME COLUMN` 은 새 열 추가 → 복사 → 옛 열 삭제 셋으로
쪼갠다. 표 이름도 같다.

### 규칙 하나

> **운영 DB 를 가리킨 `db:preflight` 가 "⚠ N건이 사라집니다"를 내면, 그 배포는
> 그날 밤 하지 않는다.**

지우는 문장을 다음 배포로 떼어 내고 나머지만 낸다. 예외는 사람이 "그 N건은 지워도
되는 자료"라고 이름을 대며 판단할 때뿐이다. `check-pending-migrations.ts` 는 이미 그
상황에서 **종료 코드 1** 을 내므로, 절차에 "종료 코드가 1이면 멈춘다"를 적기만 하면
도구가 규칙을 지킨다.

## 11. 이 문서를 쓰면서 찾은 구멍 셋

> 셋 다 **NAS 를 기다리지 않고 지금 고칠 수 있다.**

### ㄱ. ✅ ~~`app-as` 에 양식 볼륨이 없다~~ — 2026-09-14 메웠다 (compose 의 `/templates` 볼륨 · 경로 여섯 · `TZ`)

`nas/docker-compose.nas.yml` 의 `app-as` 에 붙는 마운트는
`/volume1/dss/as-attachments:/data` **하나뿐**이다. 그런데 앱은 xlsx 양식 **6개**를
호스트 경로로 읽는다 — `QUOTE_` · `OH_QUOTE_` · `MATCHER_` ×2 ·
`INSPECTION_REPORT_` · `REPAIR_REPORT_`.

지금 구성으로 NAS 를 세우면 **견적서·검사보고서·수리보고서 출력이 전부 실패한다.**

**고칠 것 둘**
- `app-as` 에 `- /volume1/dss/as-templates:/templates:ro` 추가
- `nas/env/README.md` 의 "NAS 에서 달라지는 값" 표에 `UPLOADS_DIR` · 양식 6개 · `TZ` 추가
  (지금 그 표에 이 여덟이 없다)

### ㄴ. 🔴 `db:preflight` 가 「되돌리기 불가」를 보지 못한다 — ⬜ 아직 (A/S 저장소의 일)

`RF_Service_System/src/lib/db/migration-safety.ts` 가 잡는 것은 **다섯 종**뿐이다 —
`DROP TABLE` · `TRUNCATE` · `DELETE` · `DROP COLUMN` · `DROP SCHEMA`.
전부 **자료가 사라지는가**만 본다. 그런데 되돌리기를 막는 것은 다른 집합이다.

| 구문 | 자료가 사라지나 | 옛 이미지가 도나 | 지금 preflight |
|---|---|---|---|
| `DROP COLUMN` | ✅ | ✅ | 잡는다 |
| `RENAME COLUMN` | ❌ | **❌ 즉시 깨진다** | **못 잡는다** |
| `ALTER COLUMN … TYPE` | ❌ | ❌ 대개 깨진다 | **못 잡는다** |
| `SET NOT NULL` | ❌ | **❌ 옛 코드의 INSERT 가 막힌다** | **못 잡는다** |
| `DROP CONSTRAINT` / `DROP DEFAULT` | ❌ | 경우에 따라 | **못 잡는다** |

**제안** — `migration-safety.ts` 에 두 번째 목록 `findBackwardIncompatibleOperations()`
를 더하고, preflight 가 두 줄로 나눠 보고한다:

```
[0084_…] 지우는 문장 0건 — 사라지는 자료 없음
[0084_…] ⚠ 옛 이미지로 되돌아갈 수 없게 하는 문장 1건
  · users.display_name 에 NOT NULL — 이 배포 뒤에는 태그 되돌리기가 통하지 않습니다
```

**이것이 9절의 롤백 설계와 도구를 잇는 유일한 자리다.**
`migration-safety.test.ts` 가 이미 있어 붙이기도 쉽다.

### ㄷ. ✅ ~~로그 크기 제한이 없다~~ — 2026-09-14 다섯 서비스에 `json-file` 10m × 3

`nas/docker-compose.nas.yml` 의 다섯 서비스에 `logging` 옵션이 없다. 기본값은
무제한이다. **HDD 한 장짜리 NAS 에서 로그가 `/volume1` 을 채우면 DB 가 먼저 죽는다.**
관측을 켜면서 이것을 안 켜면 관측이 사고 원인이 된다.

```yaml
    logging:
      driver: json-file
      options: { max-size: "10m", max-file: "3" }
```
