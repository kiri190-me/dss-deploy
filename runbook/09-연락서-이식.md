# 09 — 교산 연락서 469장을 운영 DB 에 넣는다

A/S 관리 시스템(`RF_Service_System`)의 일이다. **새 사이트를 띄우는 일이 아니라
이미 도는 시스템의 DB 에 과거 자료를 넣는 일**이다.

이 문서는 **아직 하지 않은 일의 절차서**다(2026-09-28 작성).

> 🔴 **이 일은 실제 자료를 운영 DB 에 넣는다.** 지금까지의 배포는 코드를 갈아
> 끼우는 일이었고 잘못되면 옛 이미지로 되돌리면 끝이었다. 이번에는 **들어간
> 자료가 남는다.** 그래서 되돌리기 도구를 먼저 만들었고(2026-09-28, 개발에서
> 4건을 실제로 지우고 확인), 회차 번호 하나로 통째로 되짚는다.

> 🔴 **PO 배포와 같은 날 하되 같은 단계로 묶지 않는다**(2026-09-28 사용자 결정).
> **연락서가 먼저**다. 그때는 PO 가 아직 안 떠 있어 움직이는 것이 적다.
> 이 문서가 끝까지 가고 **탈이 없는 것을 확인한 뒤에** `08-PO-배포.md` 로 넘어간다.
> 한 단계로 합치면 문제가 났을 때 어느 쪽 탓인지 못 가린다.

## 0. 왜 이 절차가 필요한가 — 운영 DB 는 이 PC 에서 못 닿는다

NAS 의 compose 가 DB 에 포트를 **일부러 안 열어 두었다**. 그래서 개발 PC 에서
스크립트를 돌려 운영에 넣는 길이 없다. 스크립트는 **`dss-as-tools` 컨테이너
안에서만** 돈다(`profiles: [tools]` — 부를 때만 잠깐 떴다 사라진다).

그 컨테이너가 연락서를 읽으려면 **원본 파일이 컨테이너 안에 보여야** 한다.
지금은 안 보인다. 1절이 그 목록이다.

### 원본 503장의 구성 — 개발 PC 백업 실측

```
kyosan-xlsm          360장  (.xlsm 357 + .xlsx 3)  ← NAS 공유폴더에 그대로 있다
kyosan-xls-src       143장  (.xls)                  ← NAS 에 있지만 판독기가 못 읽는다
kyosan-xls-converted 143장  (.xlsm)                 ← 🔴 개발 PC 에서 변환한 것. NAS 에 없다
```

**넣을 대상은 469장이다** — 503 − 31(엑셀 잠금 파일 `~$…`, 영영 연락서가 아니다)

⚠️ 이식 흔적에는 **원본 파일 이름도 경로도 남지 않는다.** 남는 것은 내용 해시

그렇게 적어 두었다). 그래서 변환본 143장을 NAS 어디에 두든 기록이 달라지지 않는다.

## 3. 🔴 사람이 손으로 하는 일 — 이 순서대로

### ㄱ. 운영 백업을 먼저 뜬다

🔴 **개발 백업은 운영을 지키지 못한다.**

- **DB** — `dss_as` 전체. 절차는 `runbook/07` 의 그 절.
- **첨부 파일 폴더** — `/volume1/dss/as-attachments`. 🔴 이식이 **연락서 파일을
  첨부로 붙인다**(개발 4건에서 84개가 붙었다). 되돌리기는 파일을 **지우지 않고
  치워 두지만**, 그래도 백업을 먼저 뜬다.

### ㄴ. 도구 이미지를 다시 굽고 NAS 에 올린다

```bash
# (개발 PC)
cd C:/Users/희만/Desktop/Development/RF_Service_System
git submodule status                      # 둘 다 채워져 있어야 한다
docker build --target tools -t dss-as-tools:1 .
docker save dss-as-tools:1 -o dss-as-tools-1.tar
```

```bash
# (NAS) 옮긴 뒤
sudo docker load -i dss-as-tools-1.tar
```

🔴 **실제로 새 것이 올라갔는지 확인한다** — 태그가 같아서 눈으로는 구별이 안 된다.

```bash
# (NAS) 이미지가 언제 구운 것인가 — 오늘 날짜여야 한다
sudo docker images dss-as-tools:1 --format "{{.CreatedAt}}"
# 🔴 러너가 실제로 들어 있는가
sudo docker run --rm --entrypoint sh dss-as-tools:1 -c "ls -1 /app/scripts | grep kyosan"
```

마지막 명령에 아래 넷이 **다 나와야** 한다. 하나라도 없으면 옛 이미지다.

```
import-kyosan-reports.ts
revert-kyosan-import.ts
lib/kyosan-import-run.ts      (lib 안이라 `ls /app/scripts/lib` 로 본다)
lib/kyosan-import-revert.ts
```

### ㄷ. 변환본 143장을 NAS 에 올린다

```bash
# (개발 PC) 올리기 전에 장수를 센다
find "C:/Users/희만/Desktop/_백업/2026-09-28-연락서원본/kyosan-xls-converted" -type f | wc -l
#   → 143 이어야 한다
```

`/volume1/dss/kyosan-converted` 에 올린다(DSM File Station 또는 `scp`).

```bash
# (NAS) 대조 — 개수와 총 바이트가 같아야 한다
find "/volume1/dss/kyosan-converted" -type f | wc -l
find "/volume1/dss/kyosan-converted" -type f -printf "%s\n" | awk '{s+=$1} END {print s}'
# 컨테이너가 읽을 수 있어야 한다(uid 1000)
```

⚠️ **개수만 보지 말고 총 바이트도 본다.** 파생 파일이 백업에서 빠져 있던 적이
있다(이 저장소의 지난 실측).

### ㄹ. 원본 공유폴더가 NAS 어디인지 확인한다

```bash
# (NAS)
ls -d "/volume1/2_as센터/1. 수리 관련/3. 연락서(활용)/2. 연락서"
```

⚠️ 없으면 공유 이름이 다른 것이다. DSM 의 공유폴더 목록에서 `2_as센터` 가
어느 볼륨인지 보고 경로를 고친다. **추측으로 넘어가지 마라** — 잘못된 폴더를
붙이면 러너가 「문서 아님」을 잔뜩 세고 끝난다.

🔴 **ACL 을 걷지 마라.** 견적서 공유폴더와 같은 곳이다 — 걷으면 **직원의
탐색기 접근이 끊긴다.** 대신 아래 ㅁ 에서 `group_add: ["100"]` 을 준다.
읽기 전용(`:ro`)이라 이 컨테이너가 그 폴더를 건드릴 일도 없다.

### ㅁ. `tools-as` 에 볼륨 둘과 `group_add` 를 더한다

`nas/docker-compose.nas.yml` 의 `tools-as` 에 더한다. **`app-as` 의 같은 줄을
본보기로 삼는다.**

```yaml
  tools-as:
    image: dss-as-tools:1
    profiles: [tools]
    networks: [dss-data, dss-edge]
    # ⚠️ 연락서 원본 공유폴더의 Synology ACL 때문이다 — 까닭은 app-as 의 같은 줄 주석.
    #    읽기 전용이라 이 컨테이너가 그 폴더를 건드릴 일은 없다.
    group_add: ["100"]
    env_file:
      - ./env/as.env
    environment:
      TZ: Asia/Seoul
      DATABASE_URL: postgresql://dss_app:${AS_APP_PASSWORD}@dss-pg-app:5432/dss_as
      UPLOADS_DIR: /data
    volumes:
      - /volume1/dss/as-migrations:/app/drizzle:ro
      - /volume1/dss/as-attachments:/data
      # ── 연락서 이식 (runbook/09) ────────────────────────────────────
      # 원본 360장. 🔴 읽기 전용 — 직원이 쓰는 실제 서류함이다.
      - type: bind
        source: "/volume1/2_as센터/1. 수리 관련/3. 연락서(활용)/2. 연락서"
        target: /kyosan-src
        read_only: true
      # 개발 PC 에서 .xls 를 바꾼 143장. 엑셀이 NAS 에 없어 여기로 올린다.
      - /volume1/dss/kyosan-converted:/kyosan-converted:ro
```

⚠️ 경로에 공백과 괄호가 있어 **긴 문법**으로 적는다. 짧은 문법(`"원본:대상"`)은
한 줄을 콜론으로 가르는데, 따옴표를 씌우면 이번엔 전체가 원본 하나로 읽힌다.

## 4. 🔴 넣는다 — 일곱 단계

2026-09-28 사용자 승인 절차다. **4번 없이 5번으로 가지 않는다.**

### 1) 계획만 돌린다 — `--apply` 가 없으면 한 글자도 쓰지 않는다

```bash
# (NAS)
cd /volume1/dss/deploy
sudo docker compose -f docker-compose.nas.yml --env-file .env.nas --profile tools \
  run --rm tools-as \
  node --conditions=react-server --import tsx scripts/import-kyosan-reports.ts \
    --dir /kyosan-src --dir /kyosan-converted
```

⚠️ `--conditions=react-server` 가 **반드시** 있어야 한다. 없으면 이식기 쪽
`server-only` 가 풀리지 않아 모듈을 읽는 순간 던진다.

### 2) 🔴 사람이 표를 본다 — 여기가 확인 자리다

요약에서 **반드시** 볼 것 셋:

| 무엇 | 뜻 | 이상하면 |
|---|---|---|
| **갈래별 합계** | 넣을 수 있음 / 이미 있음 / 짝 없음 / 문서 아님 / 못 읽음 | 「문서 아님」이 크면 ㄹ 의 폴더가 틀렸다 |
| 🔴 **부품 건너뛰기 장수** | 출하가 잠긴 건·반출 이력이 있는 건에서 사용 부품이 **말없이 건너뛰어진다** | 아래 ⚠️ |
| **「사람이 골라야 하는」 장수** | 짝이 하나로 안 정해진 장 | 7절 |

🔴 **부품 건너뛰기를 꼭 보라.** 이식은 실패하지 않고 **경고만 남긴다.**
개발 계획에서는 0장이었지만 **넣을 수 있는 장이 3장뿐이라 표본이 없는 것**이지
「안 일어난다」가 아니다. 운영의 469장이 가리키는 건은 **대부분 이미 출하 완료**일
가능성이 크다. 이 수가 크면 **「부품을 넣을지 말지」가 새 결정**이 된다 —
그때는 여기서 멈추고 정한다.

### 3) 승인 — 여기서 멈출 수 있다

계획이 납득되지 않으면 멈춘다. 아직 아무것도 안 들어갔다.

### 4) `--apply` 로 돌린다. 🔴 회차 번호를 받아 적는다

```bash
sudo docker compose -f docker-compose.nas.yml --env-file .env.nas --profile tools \
  run --rm tools-as \
  node --conditions=react-server --import tsx scripts/import-kyosan-reports.ts \
    --dir /kyosan-src --dir /kyosan-converted \
    --apply --out /data/kyosan-import-2026-09-28.json
```

🔴 **회차 번호(`importBatchId`)를 받아 적는다.** 러너가 **맨 처음과 맨 끝에**
찍는다. 그 번호 하나로 회차 전체를 되짚는다 — **적어 두지 않으면 되돌리기가
어려워진다.**

🔴 `--out` 은 **`/app` 밖**이어야 한다. 안이면 스크립트가 거절한다.
`/data` 는 첨부 볼륨이라 컨테이너가 사라져도 파일이 남는다.

### 5) 결과를 SQL 로 다시 본다

```bash
sudo docker exec -it dss-pg-app psql -U dss_app -d dss_as
```

🔴 **이식 흔적은 전용 표에 있지 않다.** `status_change_histories` 에
`action = 'LEGACY_IMPORT_STATE_SET'` · `metadata->>'source' = 'KYOSAN_REPORT'` 로
들어간다(2026-09-28 개발 DB 로 확인). 전용 표를 찾으면 없다.

```sql
-- ① 이 회차로 들어간 흔적이 몇 장인가 (<회차> 를 4)에서 적은 번호로)
select count(*) as 흔적
  from status_change_histories
 where metadata->>'source' = 'KYOSAN_REPORT'
   and metadata->>'importBatchId' = '<회차>';

-- ② 이 회차가 붙인 첨부와 넣은 사용 부품의 개수
select
  sum(jsonb_array_length(coalesce(metadata->'attachmentIds', '[]'::jsonb))) as 첨부,
  sum(jsonb_array_length(coalesce(metadata->'usedPartIds',   '[]'::jsonb))) as 사용부품
  from status_change_histories
 where metadata->>'source' = 'KYOSAN_REPORT'
   and metadata->>'importBatchId' = '<회차>';

-- ③ 🔴 회차 번호가 안 실린 흔적이 있는가 — 있으면 되돌리기가 그 장을 놓친다
select count(*) as 회차없는흔적
  from status_change_histories
 where metadata->>'source' = 'KYOSAN_REPORT'
   and metadata->>'importBatchId' is null;
```

🔴 **③ 은 넣기 전에 먼저 세어 둔다.** 회차 번호가 없는 흔적은 `--batch` 로
되돌려지지 않는다. 화면(`/excel-imports/kyosan-report`)으로 한 장씩 넣은 옛 장이
있으면 0 이 아닌 것이 정상이다 — 개발 DB 실측도 **4장**이 그렇다(회차 번호를
싣는 기능이 2026-09-28 에 생겼기 때문이다).

그래서 보는 법은 「0 인가」가 아니라 **「넣기 전과 뒤가 같은가」**다.
늘었다면 회차 번호가 안 실린 것이고, 그 장들은 손으로 되돌려야 한다
(`revert-kyosan-import.ts --case <접수번호>`).

```sql
-- 넣기 전과 뒤에 각각 돌려 같은 수인지 본다
select count(*) from status_change_histories
 where metadata->>'source' = 'KYOSAN_REPORT'
   and metadata->>'importBatchId' is null;
```

⚠️ 칸 이름은 `usedPartIds` · `attachmentIds` · `importBatchId` · `sourceSha256`
이고 2026-09-28 기준이다. 실제로 무엇이 실리는지는
`src/lib/server/services/kyosan-report-import.ts` 의 `metadata:` 블록이 원본이다.

## 6. 🔴 「사람이 골라야 하는」 장 — 러너가 넣지 않는다

연락서의 접수번호로 짝이 **딱 하나로 정해지지 않으면** 이식기가 넣지 않는다.
후보가 있어도 「사람이 고른다」가 설계다.

**러너에 「자동으로 고르는 길」을 만들지 않는다**(2026-09-28 사용자 결정).
만드는 순간 「짝이 정해지지 않으면 넣지 않는다」가 배치에서만 풀린다 —
잘못 붙으면 **남의 수리 건에 남의 연락서가 들어간다.**

그 장들은 화면에서 한 장씩 처리한다:

```
A/S → /excel-imports/kyosan-report → 후보를 보고 고른다
```

### D210103 은 손으로 넣는다

그 파일의 접수번호 칸은 `D210104` 인데 **그 건이 없다.** S/N 으로 찾은 후보
1건(`D210103`)은 **모델·S/N·L/N 이 다 맞지만 고객사가 다르다.** 그래서
자동으로 고르면 안 되는 대표 사례다 — 사람이 화면에서 보고 정한다.

⚠️ **운영 계획에서 이 갈래가 수십 장 나오면** 「후보가 딱 1건이고 모델·S/N·L/N 이
전부 일치할 때만 자동으로 고른다」를 러너에 더할지 **그때 정한다.**
개발에서는 16장이었다.
