# 06 — 개선요청 사이트를 NAS 에 올린다 (첫 배포)

넷째 사이트다. 저장소는 `C:\Users\희만\Desktop\Development\dss-improvements`,
GitHub 이름도 `dss-improvements`, 사내 이름은 **개선요청**이다.

이 문서는 **아직 하지 않은 일의 절차서**다(2026-09-18 작성). 여기 적힌 것은
`nas/docker-compose.nas.yml` 에 서비스 둘을 더한 것까지이고, NAS 에서는 아직
아무것도 돌지 않았다.

> 🔴 **그 서비스 둘은 지금 「주석 처리」돼 있다**(2026-09-18, 첫 설치를 다른 날로
> 미루면서). `env/improvements.env` 가 NAS 에 없는데 켜 두면 `docker compose`
> 명령이 **통째로** 안 먹기 때문이다. 첫 설치를 할 때 **2-ㅇ 에서 벗긴다.**

> 🔴 **이 문서의 절반은 파일로 만들 수 없는 일이다.** DNS · 리버스 프록시 ·
> 시크릿 발급 · 이미 돌아가는 DB 에 롤 만들기는 사람이 손으로 한다.
> 2절이 그 목록이고, 배포하는 사람은 **2절만 보고 따라 할 수 있어야 한다.**

## 0. 왜 「배포」가 아니라 「첫 배포」인가

지금까지의 배포(`07`~`09-deploy.sh`)는 **이미 서 있는 것을 갈아 끼우는 일**이었다.
이번에는 없던 것이 생긴다. 그래서 평소 배포에 없는 여섯이 앞에 붙는다.

| | 평소 배포 | 첫 배포 |
|---|---|---|
| DB | 이미 있다 | **롤·DB 를 손으로 만든다** (2-ㄴ) |
| 파일 볼륨 | 이미 있다 | **폴더를 만들고 권한을 준다** (2-ㄷ) |
| 포털 | 이미 등록돼 있다 | **clients 에 줄을 넣고 시크릿을 발급한다** (2-ㄹ) |
| 주소 | 이미 닿는다 | **DNS 한 줄 + 프록시 규칙 하나** (2-ㅁ·ㅂ) |
| 설정 파일 | 이미 NAS 에 있다 | **`env/improvements.env` 를 만들어 올린다** (2-ㅅ) |
| compose | 서비스가 이미 켜져 있다 | **주석 세 자리를 벗겨 올린다** (2-ㅇ) |

## 1. 미리 정해 둔 것

`nas/docker-compose.nas.yml` 에 이미 적혀 있다. 여기서 바꿀 것이 아니라,
**손으로 만드는 것들이 이 값과 글자 단위로 맞아야 한다.**

| | 값 | 어디에 적혀 있나 |
|---|---|---|
| 운영 이미지 | `dss-improvements:0.1` | 그 저장소 `Dockerfile` 머리말 |
| 도구 이미지 | `dss-improvements-tools:1` | 같은 파일의 `tools` 스테이지 |
| 컨테이너 이름 | `dss-improvements` | compose |
| 앱 포트 | 컨테이너 안 `3500` → `127.0.0.1:13500` | compose (원칙 2 — 앞에 1 을 붙인 번호) |
| 사내 주소 | `https://improvements.dss21.co.kr` | 이 문서 2-ㅁ·ㅂ |
| DB | `dss_improvements` · 롤 `dss_improvements_app` · 인스턴스 **`dss-pg-app`**(공용) | `nas/init/app/01-roles.sh` |
| 업로드 폴더 | NAS `/volume1/dss/improvements-uploads` → 컨테이너 `/data/uploads` | compose |
| 설정 파일 | `/volume1/dss/deploy/env/improvements.env` (root 600) | `nas/env/README.md` |
| 비밀번호 | `.env.nas` 의 `IMPROVEMENTS_APP_PASSWORD` | `nas/.env.nas.example` |
| 역할 | `ADMIN` · `MEMBER` | 그 저장소 `src/lib/db/schema.ts` 의 `USER_ROLES` |
| 메모리 | 384M (도구 512M) | compose |

**왜 공용 인스턴스(`dss-pg-app`)인가** — A/S(`dss_as`)와 계측기(`dss_meters`)가
이미 그 안에 있고 롤이 서로의 DB 에 닿지 못한다(런북 01 6절, 격리 검증 실측).
개발 PC 에서 쓰는 전용 상자(5446)는 그 결정이 나기 전까지 혼자 서서 개발하려고
둔 것이다 — 그 저장소 `docker-compose.yml` 머리말이 그렇게 적어 두었다.
NAS 에 상자를 하나 더 띄우면 6GB 예산에서 postgres 하나 값(300~700M)을 더 쓴다.

## 2. 🔴 사람이 손으로 하는 일 — 이 순서대로

아래 ㄱ~ㅇ 을 다 한 뒤에 3절(이미지)로 간다. 순서를 바꾸면 앞의 것이 뒤의
것을 기다리게 된다(특히 ㄹ 의 시크릿은 ㅅ 의 파일에 들어가야 하고,
**ㅇ 은 ㅅ 뒤여야 한다** — 설정 파일이 NAS 에 없는데 주석을 벗기면
`docker compose` 가 통째로 안 먹는다).

### ㄱ. 비밀번호 한 줄 — `.env.nas`

```bash
# (개발 PC) 값을 만든다. 다른 넷과 달라야 한다 — 초기화 스크립트가 겹치면 거절한다
node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"
```

이 값을 **NAS 의 `/volume1/dss/deploy/.env.nas`** 와 **개발 PC 의 `nas/.env.nas`**
양쪽에 `IMPROVEMENTS_APP_PASSWORD=` 한 줄로 더한다. NAS 쪽은 root 600 이라
`setup/incoming/` 에 올려 두고 사람이 `sudo` 로 옮긴다.

> ⚠️ 개발 PC 쪽에도 더하는 이유: `docker-compose.rehearsal.yml` 이 NAS 파일의
> `db-app` 을 `extends` 로 끌어다 쓴다. 줄이 없으면 compose 가 "variable is not
> set" 경고를 내고 빈 값으로 조립한다.

### ㄴ. 🔴 롤과 DB — 이미 돌아가는 인스턴스라 손으로 만든다

**`nas/init/app/01-roles.sh` 는 볼륨이 빌 때 한 번만 도는 스크립트다.**
NAS 의 `dss-pg-app` 은 2026-09-14 에 이미 만들어졌으므로 그 파일을 고쳐도
**저절로 적용되지 않는다.** 이 절을 건너뛰면 DB 가 없어 앱이 뜨자마자 죽는다.

```bash
# (NAS · 사람 · sudo -i)
set -a; . /volume1/dss/deploy/.env.nas; set +a     # 값은 화면에 찍지 않는다

/usr/local/bin/docker exec -i dss-pg-app \
  psql -X -q -v ON_ERROR_STOP=1 -U "$APP_POSTGRES_USER" -d postgres <<'SQL'
CREATE ROLE dss_improvements_app LOGIN;

CREATE DATABASE dss_improvements
  OWNER dss_improvements_app
  ENCODING 'UTF8'
  LOCALE_PROVIDER icu ICU_LOCALE 'ko-KR'
  LOCALE 'C.UTF-8'
  TEMPLATE template0;

REVOKE CONNECT ON DATABASE dss_improvements FROM PUBLIC;
GRANT  CONNECT ON DATABASE dss_improvements TO dss_improvements_app;
SQL
```

비밀번호는 위 SQL 에 적지 않는다 — 명령줄에 적으면 `ps` 에 잠깐 보인다.
대신 psql 안에서 물어보게 한다(입력한 글자가 화면에 보이지 않는다):

```bash
/usr/local/bin/docker exec -it dss-pg-app \
  psql -X -U "$APP_POSTGRES_USER" -d postgres -c '\password dss_improvements_app'
```

`.env.nas` 에 적은 값과 **글자 하나까지 같아야 한다.** 맞는지는 4절에서
앱이 뜨는 것으로 확인된다 — 틀리면 로그에 `password authentication failed`
가 찍힌다.

확인:

```bash
/usr/local/bin/docker exec dss-pg-app psql -X -At -U "$APP_POSTGRES_USER" -d postgres \
  -c "select datname, pg_get_userbyid(datdba) from pg_database where datname like 'dss_%' order by 1"
# → dss_as|dss_app · dss_improvements|dss_improvements_app · dss_meters|dss_meters_app
```

격리도 본다 — 다른 롤이 새 DB 에 닿으면 안 된다(런북 01 6절과 같은 시험).

### ㄷ. 업로드 폴더 — 🔴 이것이 빠지면 올린 스크린샷이 사라진다

스크린샷의 바이트는 `UPLOADS_DIR` 아래 놓이고 DB 에는 **그 루트 기준 상대
경로만** 적힌다. 볼륨이 없으면 파일은 컨테이너 안 임시 디스크에 쌓이고,
다음 배포에서 컨테이너를 새로 만드는 순간 전부 사라진다 — 화면에는 첨부가
있는데 바이트만 없는 상태가 된다.

경로 관례는 계측기·A/S 에서 그대로 가져왔다(`/volume1/dss/<시스템>-<용도>`).
권한도 `01-prepare.sh` 2단계가 `meters-files`·`as-attachments` 에 한 것과 같다 —
Synology ACL 을 걷고 컨테이너의 node(uid 1000)에게 준다.

```bash
# (NAS · 사람 · sudo -i)
D=/volume1/dss
mkdir -p "$D/improvements-uploads"
find "$D/improvements-uploads" -exec /usr/syno/bin/synoacltool -del {} \; >/dev/null 2>&1
chown -R 1000:1000 "$D/improvements-uploads"
chmod 750 "$D/improvements-uploads"
stat -c '%U:%G %a' "$D/improvements-uploads"      # → 1000:1000 750 (이름이 없으면 숫자로 보인다)
/usr/syno/bin/synoacltool -get "$D/improvements-uploads" | grep -c ':\(allow\|deny\):'   # → 0
```

이미지를 불러온 뒤(3절) 실제로 써지는지도 본다 — `01-prepare.sh` 4단계와 같은 방식:

```bash
/usr/local/bin/docker run --rm --network none --user 1000:1000 \
  -v "$D/improvements-uploads:/data/uploads" --entrypoint sh dss-improvements:0.1 \
  -c 'touch /data/uploads/.probe && rm /data/uploads/.probe' && echo "쓰기 OK"
```

### ㄹ. 🔴 포털에 사이트 등록 — 시크릿 발급

**여기에 구멍이 하나 있다.** 포털(`dss-auth`)의 등록 명령 `npm run client:register`
는 `tsx` 로 도는 스크립트인데, NAS 의 운영 이미지에는 `tsx` 가 없다. A/S·계측기와
달리 **포털에는 도구 이미지(`tools-auth`)가 없다** — 그 저장소 `Dockerfile` 에
`tools` 스테이지가 없다. 그래서 NAS 에서는 **SQL 로 직접 넣는다.**

시크릿은 개발 PC 에서 만들어 **설정 파일에 바로 적고, 해시만 NAS 로 들고 간다.**
평문은 화면에 찍지 않는다(`nas/env/README.md` 「비밀값을 옮길 때」).

```bash
# (개발 PC · nas/env 에서) 시크릿을 파일에 직접 적고 해시만 출력한다
node -e "const c=require('crypto'),fs=require('fs');const s=c.randomBytes(32).toString('base64url');fs.appendFileSync('improvements.env','SSO_CLIENT_SECRET='+s+'\n');console.log(c.createHash('sha256').update(s,'utf8').digest('hex'))"
```

```sql
-- (NAS) docker exec -i dss-pg-auth psql -X -q -v ON_ERROR_STOP=1 -U dss_auth_app -d dss_auth
INSERT INTO clients (
  client_id, name, description, client_secret_hash,
  redirect_uris, post_logout_redirect_uris, backchannel_logout_uri,
  requires_grant, available_roles, is_active, launcher_url, launcher_icon, sort_order
) VALUES (
  'dss-improvements',
  'DSS 개선요청',
  '사내 시스템에 바라는 것을 적는 곳',
  '<위에서 나온 sha256 hex>',
  ARRAY['https://improvements.dss21.co.kr/api/auth/sso/callback'],
  '{}',                                    -- 이 사이트는 post_logout_redirect_uri 를 보내지 않는다
  'https://improvements.dss21.co.kr/api/auth/sso/backchannel-logout',
  false,                                   -- 아래 ⚠️ 를 읽고 고른다
  ARRAY['ADMIN','MEMBER'],
  true,
  'https://improvements.dss21.co.kr/',
  '💡',
  400
);
```

⚠️ **`requires_grant` 는 사람이 고를 자리다.**

| 값 | 뜻 | 누가 ADMIN 이 되나 |
|---|---|---|
| `false` | 포털에 로그인할 수 있는 **모든 직원**이 쓴다 | 역할 클레임이 없으므로 **전원 MEMBER**. 첫 관리자는 아래 SQL 로 |
| `true` | `user_client_grants` 에 이름이 있는 사람만 | 부여할 때 `role='ADMIN'` 을 같이 준다 |

개선요청은 **모두가 적는 곳**이라 `false` 가 성격에 맞는다. 그 대신 첫 관리자를
손으로 세운다 — 그 사람이 **한 번 로그인한 뒤에** (그때 `web_users` 행이 생긴다):

```sql
-- (NAS) docker exec -i dss-pg-app psql -X -U dss_improvements_app -d dss_improvements
UPDATE web_users SET role = 'ADMIN', updated_at = now() WHERE email = '<그 사람 메일>';
```

`true` 를 골랐다면 대신 명단을 넣는다:

```sql
-- (NAS) 인증 DB 에서. users.email 은 포털에 등록된 값이다
INSERT INTO user_client_grants (user_id, client_id, role, granted_by)
SELECT u.id, c.id, 'ADMIN', g.id
FROM users u, clients c, users g
WHERE u.email = '<받는 사람>' AND g.email = '<주는 사람>'
  AND c.client_id = 'dss-improvements';
```

> 📌 **더 나은 길 — 다음에 포털을 손볼 때.** `dss-auth/Dockerfile` 에 `tools`
> 스테이지를 더하고 compose 에 `tools-auth` 를 두면, 위 INSERT 들이
> `npm run client:register` · `npm run client:grant` 한 줄로 바뀐다(감사 로그도
> 그쪽이 남긴다). **그것은 이 저장소가 아니라 `dss-auth` 의 일이다.**

### ㅁ. 🔴 DNS — Cloudflare 에 A 레코드 하나

`https://improvements.dss21.co.kr` 가 `192.168.0.222` 를 가리켜야 한다.
**인증서는 새로 받지 않는다** — 이미 있는 와일드카드 `*.dss21.co.kr` 가 덮는다
(2026-09-15, 런북 README ①).

1. Cloudflare → `dss21.co.kr` → DNS → 레코드 추가
2. 형식 **A** · 이름 **`improvements`** · 내용 **`192.168.0.222`**
3. **프록시 끔(회색 구름)** — 켜면 Cloudflare 가 사설 IP 로 못 간다
4. 사내 PC 에서 `nslookup improvements.dss21.co.kr` → `192.168.0.222`

### ㅂ. 🔴 DSM 리버스 프록시 — 규칙 하나

**DSM 관리 화면에서 사람이 손으로 한다.** 파일로 만들 수 없다.
기존 셋(`login`·`as`·`meters`)과 같은 모양으로 넣는다.

1. DSM → 제어판 → 로그인 포털 → 고급 → **리버스 프록시** → 만들기
2. 설명 `DSS 개선요청 (https)`
3. **소스** — 프로토콜 `HTTPS` · 호스트 이름 **`improvements.dss21.co.kr`** · 포트 `443`
4. **대상** — 프로토콜 `HTTP` · 호스트 이름 **`localhost`** · 포트 **`13500`**
5. HSTS 끔 · WebSocket 머리글 없음 (이 앱도 쓰지 않는다)
6. 제어판 → 보안 → **인증서** → 설정 → 새 규칙에 **`dss21.co.kr`** 인증서를 지정
   (기본값은 `synology.com` 이다 — 09-15 에 여기서 한 번 걸렸다)

> ⚠️ **http 규칙은 만들지 않는다.** 옛 `192.168.0.222:3000·3100·3300` 규칙은
> 되돌리기용으로 남아 있는 것이고(README ②표 10), 새 사이트에는 되돌릴 옛 주소가
> 없다. http 로 들어오면 `SESSION_COOKIE_SECURE=true` 때문에 로그인이 **조용히**
> 실패한다.

### ㅅ. 설정 파일 — `env/improvements.env`

`dss-improvements/.env.example` 을 복사해 만든다(`nas/env/README.md`).
NAS 에서 달라지는 값만 적으면 이렇다.

| 항목 | 값 | 왜 |
|---|---|---|
| `DATABASE_URL` | **지운다** | compose 가 `.env.nas` 의 비밀번호로 조립해 넘긴다 |
| `DEV_POSTGRES_PASSWORD` | **지운다** | 개발 PC 의 DB 상자를 띄우는 값이다. NAS 에는 그 상자가 없다 |
| `PORT` | **지운다** | 이미지가 `ENV PORT=3500` 으로 들고 있다 |
| `UPLOADS_DIR` | **지운다** | compose 가 넘긴다(볼륨과 짝이라 한 파일에 있어야 한다) |
| `AUTH_SESSION_SECRET` | **새로 만든다** (32자 이상) | 개발과 운영이 같은 비밀을 쓰지 않는다. 바꾸면 나가 있는 세션이 전부 무효 |
| `SSO_TX_SECRET` | **새로 만든다** (32자 이상) | 위와 **다른 값**이어야 한다 |
| `SESSION_COOKIE_SECURE` | **`true`** | 사내 주소가 https 다. 계측기가 이미 `true` 다 |
| `SESSION_HOURS` | `12` | 포털 세션의 절대 만료를 넘기지 않는다 |
| `SSO_ISSUER` | **`https://login.dss21.co.kr`** | `auto` 는 컨테이너 안에서 172.x 를 잡는다 — 그러면 `iss` 대조가 실패한다 |
| `SSO_CLIENT_ID` | `dss-improvements` | 2-ㄹ 에서 넣은 값과 글자 단위로 같아야 한다 |
| `SSO_CLIENT_SECRET` | 2-ㄹ 에서 만든 평문 | DB 에는 해시만 있다. 잃어버리면 재발급뿐 |
| `SSO_REDIRECT_URI` | **`https://improvements.dss21.co.kr/api/auth/sso/callback`** | 포털이 **글자 단위로** 대조한다. `auto` 금지 |

올리는 법은 평소와 같다 — `setup/incoming/` 에 올리고 **바로 `chmod 600`**,
그다음 사람이 `sudo` 로 `deploy/env/` 로 옮긴다(그 폴더는 777 이라 옮겨지기
전까지 누구나 읽는다).

### ㅇ. 🔴 compose 의 주석 세 자리를 벗긴다 — **ㅅ 다음에** 한다

`nas/docker-compose.nas.yml` 의 개선요청 자리 **셋은 지금 주석 처리돼 있다**
(2026-09-18, 첫 설치를 다른 날로 미루면서). 벗기지 않으면 3~5절이 전부 헛돈다 —
`app-improvements` 도 `tools-improvements` 도 compose 에 **없는 서비스**이기 때문이다.

| | 자리 | 무엇이 주석인가 |
|---|---|---|
| ① | `db-app` 의 `environment` | `IMPROVEMENTS_APP_PASSWORD: ${IMPROVEMENTS_APP_PASSWORD}` 한 줄 |
| ② | 서비스 | `app-improvements` 전체 |
| ③ | 서비스 | `tools-improvements` 전체 |

> 🔴 **셋을 함께 벗긴다. 하나만 벗기면 또 깨진다.**
> ②③ 은 `./env/improvements.env` 를 가리키므로 **ㅅ 이 끝난 뒤**에 벗겨야 한다 —
> 없는 `env_file` 하나면 `docker compose` 명령이 **통째로** 실패한다(멈춘 앱을
> 다시 띄우지도 못한다). ① 은 이유가 다르다: 그 줄이 `db-app` 의 **설정 지문**을
> 바꾸므로, 꺼 둔 동안에는 인자 없는 `up -d` 에도 운영 DB 가 재생성되지 않았다.
> 벗긴 뒤부터는 4절의 `--no-deps` 경고가 다시 살아난다.

벗기는 법은 기계적이다 — **그 줄들의 맨 앞 두 칸 뒤(①은 여섯 칸 뒤)에 붙은
`# ` 두 글자만 지운다.** 왜 주석인지 설명하는 문단은 코드가 아니므로 그대로 둬도
되고 지워도 된다. 각 자리 바로 위에 「개선요청 ①/셋 · ②/셋 · ③/셋」 표시가 있다.

확인 — 벗긴 뒤 **개발 PC 에서** 먼저 본다(ㅅ 에서 `nas/env/improvements.env` 를
만들었으므로 여기서 읽힌다):

```bash
cd C:/Users/희만/Desktop/Development/dss-deploy/nas
docker compose -f docker-compose.nas.yml --env-file .env.nas --profile tools config --services | sort
# → 아홉 줄. app-improvements 와 tools-improvements 가 보여야 한다
#   (벗기기 전에는 일곱이었다)
```

그다음 **NAS 에 올린다** — 평소 배포와 같은 길이다. `setup/incoming/docker-compose.nas.yml`
에 올려 두면 배포 스크립트(`10-deploy.sh` 1-ㄴ)가 **바꾸기 전에 문법과 `env_file`
존재를 먼저 검사한 뒤** 갈아 끼우고 옛 파일을 `backups/` 에 남긴다. 배포 스크립트를
쓰지 않는다면 사람이 `sudo` 로 `deploy/docker-compose.nas.yml` 에 옮기고
(root:root 644) 옛 파일을 먼저 복사해 둔다.

## 3. 이미지 — 개발 PC 에서 굽고 옮긴다

절차는 `runbook/02-이미지-빌드.md` · `05-배포-리허설.md` 7절(G5)과 같다.
**이번에는 둘을 굽는다** — 운영 이미지와 도구 이미지.

> 🔴 **`git archive HEAD` 로 뽑지 않는다 — 이 저장소만 다르다.** 평소 배포는
> 커밋된 상태만 `git archive` 로 뽑아 굽지만(README 「다음 배포 때」 1),
> 이 저장소에는 **서브모듈 `vendor/dss-ui`** 가 붙는다(서비스 메뉴바, 2026-09-18
> 작업 중). **`git archive` 는 서브모듈의 내용을 담지 않는다** — 그렇게 뽑은
> 사본으로 구우면 `@dss/ui` 를 찾지 못해 빌드가 깨지거나, 더 나쁘게는 메뉴바만
> 빠진 이미지가 나온다. 커밋된 상태로 굽고 싶으면 별도 폴더에
> `git clone --recursive`(또는 `git submodule update --init`) 한 작업본에서 굽는다.
> `.dockerignore` 는 `vendor/` 를 막지 않으므로 작업 폴더에서 그대로 구워도 된다.

```bash
# (개발 PC) 커밋된 상태만 뽑아서 굽는다
cd C:/Users/희만/Desktop/Development/dss-improvements
docker build -t dss-improvements:0.1 .
docker build --target tools -t dss-improvements-tools:1 .

docker save dss-improvements:0.1       | gzip -1 > dss-improvements-0.1.tar.gz
docker save dss-improvements-tools:1   | gzip -1 > dss-improvements-tools-1.tar.gz

# NAS 에서 맞춰 볼 지문은 tar 가 들고 있다 (.Id 가 아니다 — README 「다음 배포 때」 2)
tar -xzOf dss-improvements-0.1.tar.gz manifest.json      # .[0].Config → 이 값이 NAS 의 image ID

# scp 는 DSM 에서 안 붙는다. ssh 표준입력으로 보낸다
ssh dss-nas "cat > /volume1/dss/images/dss-improvements-0.1.tar.gz" < dss-improvements-0.1.tar.gz
```

```bash
# (NAS · 사람 · sudo)
/usr/local/bin/docker load -i /volume1/dss/images/dss-improvements-0.1.tar.gz
/usr/local/bin/docker load -i /volume1/dss/images/dss-improvements-tools-1.tar.gz
/usr/local/bin/docker image inspect dss-improvements:0.1 --format '{{.Id}}'   # 위 Config 와 같아야 한다
```

> ⚠️ **도구 이미지는 여기서만 예외적으로 매번 옮긴다.** A/S 는 `drizzle/` 을
> 볼륨으로 붙여 도구 이미지를 그대로 두지만, 이 저장소는 `Dockerfile` 이
> `tools` 스테이지 안에 `drizzle/` 을 함께 굽는다(계측기와 같은 모양).
> **마이그레이션이 늘면 도구 이미지를 다시 구워야 한다.**

## 4. 띄운다 — 마이그레이션이 먼저다

새 DB 는 비어 있다. 표를 만들기 전에 앱을 띄우면 첫 화면에서 죽는다.

```bash
# (NAS · 사람 · sudo) /volume1/dss/deploy 에서
C="/usr/local/bin/docker compose -f docker-compose.nas.yml --env-file .env.nas"

# ① 마이그레이션 — 부를 때만 잠깐 떴다 사라진다
$C --profile tools run --rm tools-improvements npm run db:migrate

# ② 확인 — 표가 생겼나 (마이그레이션 셋: 0000·0001·0002)
/usr/local/bin/docker exec dss-pg-app psql -X -At -U dss_improvements_app \
  -d dss_improvements -c "select count(*) from information_schema.tables where table_schema='public'"

# ③ 앱만 띄운다. 다른 다섯은 건드리지 않는다
$C up -d --no-deps app-improvements
```

> ⚠️ **`--no-deps` 를 반드시 붙인다.** `db-app` 의 environment 에
> `IMPROVEMENTS_APP_PASSWORD` 한 줄이 **2-ㅇ 에서 되살아나** 그 서비스의 설정 지문이 바뀐다
> (초기화 스크립트가 그 값을 요구하기 때문이다 — 볼륨을 비우고 다시 세울 때 쓰인다).
> `--no-deps` 없이 부르면 compose 가 그 차이를 보고 **운영 DB 컨테이너를 다시
> 만든다.** 자료는 볼륨에 있어 사라지지 않지만 세 사이트가 잠깐 끊긴다.
>
> ⚠️ 같은 이유로 `docker compose up -d` 를 **인자 없이** 부르지 않는다.

## 5. 확인 — 이 순서로 본다

| | 무엇 | 어떻게 | 통과 |
|---|---|---|---|
| 1 | 컨테이너가 **대답하는가** | `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:13500/` | 2xx/3xx. `docker ps` 에 보이는 것과 대답하는 것은 다르다 |
| 2 | 사내망에 포트가 새지 않았나 | `netstat -tln \| grep 13500` | `127.0.0.1:13500` 만 |
| 3 | 밖에서 주소가 닿나 | 브라우저로 `https://improvements.dss21.co.kr` | 로그인 화면 |
| 4 | 로그인 왕복 | 포털을 거쳐 돌아온다 | 목록 화면. 실패하면 `redirect_uri` 글자 대조부터 |
| 5 | 🔴 **첨부가 NAS 에 남는가** | 글 하나에 스크린샷을 붙이고 → `find /volume1/dss/improvements-uploads -type f` | 파일이 **NAS 폴더에** 보인다. 여기가 이번 배포의 핵심이다 |
| 6 | 다시 띄워도 남는가 | `$C up -d --force-recreate app-improvements` → 그 글을 다시 연다 | 사진이 그대로 보인다 |
| 7 | 남의 것이 흔들리지 않았나 | 세 사이트 로그인·화면 | 평소대로 |

## 6. 되돌리기

첫 배포라 「옛 이미지로 내린다」가 없다. 되돌리기는 **없던 것으로 돌리는 것**이다.

```bash
$C stop app-improvements && $C rm -f app-improvements
```

앱만 내리면 DB·폴더·포털 등록은 남는다(해가 없다). 완전히 거두려면
`clients` 의 그 줄을 `is_active = false` 로 하고, DB 는 **지우지 말고 덤프를
떠 둔 뒤에** 판단한다.
