# 이미지 만들기 — 개발 PC에서 굽고, NAS에서 돌린다

3단계 문서. NAS 이식에서 **앱을 옮기는 방법**을 다룬다.

이 문서가 있는 이유는 질문 하나 때문이다 — *"개발 PC에서 이미지를 빌드한다면,
서버가 돌려면 개발 PC가 계속 켜져 있어야 하나?"*

**아니다. 오히려 반대다.** 지금이 개발 PC가 켜져 있어야 하는 상황이고,
NAS로 옮기면 그러지 않아도 된다. 그게 이 이식의 목적이다.

---

## 1. 빌드와 실행은 다른 일이다

| | 빌드(build) | 실행(run) |
|---|---|---|
| 하는 일 | 소스 코드를 **실행 가능한 덩어리로 굽는다** | 그 덩어리를 **띄워서 서비스한다** |
| 언제 | 코드를 고쳤을 때 **한 번** | **계속** |
| 어디서 | 개발 PC | NAS |
| 걸리는 시간 | 1~3분 | — (계속 떠 있음) |

**이미지(image)**가 그 결과물이다. 앱 코드·Node 런타임·필요한 도구가 전부 들어간,
**설치 CD 한 장** 같은 것. 한 번 구워 두면 그 자체로 완결돼 있다.

```
개발 PC                              NAS
───────                              ───
소스 코드
   │  docker build      (2분)
   ▼
이미지 (설치 CD)
   │  파일로 저장 → 복사 → 불러오기
   ╰────────────────────────────────▶ 이미지 보관
                                        │  docker run
                                        ▼
                                     컨테이너가 계속 돈다
                                     ← 이제 개발 PC는 꺼도 된다
```

**개발 PC가 필요한 때는 코드를 고쳐 새 버전을 낼 때뿐이다.** 평소 운영에는
전혀 관여하지 않는다.

---

## 2. 지금과 무엇이 달라지나

지금은 **개발 PC가 곧 서버다.** `작업 시작` 메뉴가 `npm run dev`를 띄우고,
그 창을 닫으면 사이트가 죽는다. PC를 끄면 아무도 못 쓴다. 계측기 시스템은
아예 이남준 님 PC에서 돌고 있다.

옮기고 나면 **NAS만 켜져 있으면 된다.** NAS는 원래 24시간 켜 두는 장비다.

| | 지금 | NAS 이식 후 |
|---|---|---|
| 서버가 도는 곳 | 개발 PC (`npm run dev`) | NAS 컨테이너 |
| PC를 끄면 | 사이트가 죽는다 | 아무 일 없다 |
| 개발 PC의 역할 | 서버 + 개발 | **개발과 빌드만** |

---

## 3. 왜 NAS에서 빌드하지 않나

기술적으로 못 할 것은 없다. 하지 않는 이유가 둘이다.

- **느리거나 죽는다.** DS218+의 Celeron J3355는 2코어 2.0GHz다. `next build`를
  돌리면 20분이 넘거나 메모리 부족으로 죽는다. 개발 PC에서 2분이면 될 일이다.
- **빌드가 운영을 방해한다.** 빌드는 순간적으로 메모리를 크게 먹는다. NAS에서
  빌드하면 그동안 돌던 다른 시스템이 함께 느려진다. 운영 장비에서 할 일이 아니다.

---

## 4. 옮기는 두 가지 길

### ㄱ. 파일로 옮긴다 (권장 — 처음에는 이쪽)

```bash
# 개발 PC에서
docker build -t dss-auth:1.0 .
docker save dss-auth:1.0 -o dss-auth-1.0.tar

# 파일을 NAS 공유폴더에 복사한 뒤, NAS에서
docker load -i dss-auth-1.0.tar
```

계정도 인터넷 접속도 필요 없다. 파일 하나가 오갈 뿐이다.
**단점은 파일이 크다는 것**(수백 MB) — 그래서 `standalone` 빌드가 중요하다.

### ㄴ. 레지스트리를 거친다 (나중에)

GitHub Container Registry 같은 곳에 올려 두고 NAS가 내려받는 방식.
자동화하기 좋지만 계정·권한·비공개 설정이 따라붙는다.
**시스템이 셋인 지금은 과하다.** 배포가 잦아지면 그때 옮긴다.

---

## 5. 버전을 붙인다 — 되돌리기가 태그 하나

이미지에 `:1.0`처럼 **버전을 붙이고, 옛 버전을 지우지 않는다.**

새 버전에 문제가 생기면 되돌리기가 이렇게 끝난다.

```bash
# compose 파일의 image 태그를 1.0 으로 되돌리고
docker compose up -d
```

`latest` 하나만 쓰면 이 길이 사라진다. 무엇이 돌고 있는지도 알 수 없게 된다.

## 6. 3단계에서 할 일

| | 할 일 | 어디 |
|---|---|---|
| 1 | `output: "standalone"` 추가 | `RF_Service_System/next.config.ts` |
| 2 | `Dockerfile` 작성 (멀티스테이지) | `dss-auth` · `RF_Service_System` · `njlee` |
| 3 | 이미지에 `postgresql-client-17` 설치 | 위 세 `Dockerfile` |
| 4 | 개발 PC에서 빌드하고 크기 확인 | 개발 PC |

### 1번이 필요한 이유

네 저장소 중 **A/S만 `output: "standalone"`이 없다.** 이게 없으면 이미지에
`node_modules`가 통째로 들어가 몇 배로 커진다. 나머지 셋은 이미 있다.

### 3번이 필요한 이유

`BACKUP_MODE=direct`가 `pg_dump`를 부르는데 Node 이미지에는 없다.
**서버가 PostgreSQL 17이므로 클라이언트도 17이어야 한다** — 낮으면 거절당한다.

이 작업을 해야 `direct` 모드가 **처음으로 실제로 돈다.** 지금은 개발 PC에
클라이언트가 없어 경로 구성과 오류 안내까지만 확인된 상태다.
자세한 것은 [`01-postgres-통합.md`](./01-postgres-통합.md) 11절.

## 7. 실제로 해 보고 알게 된 것 (2026-09-02)

세 이미지를 만들어 봤다. `dss-auth:1.0` · `dss-as:1.0` · `dss-meters:1.0`,
각 **490MB 안팎**이고 셋 다 `pg_dump 17.11`을 답한다.

### ① 빌드가 환경변수 없이는 안 된다 — 첫 시도가 여기서 죽었다

```
Error: Failed to collect page data for /apps
  [cause]: DATABASE_URL is not set.
```

`next build`는 각 화면의 데이터를 모으려고 **서버 모듈을 실제로 불러온다.**
DB 클라이언트 모듈이 읽히는 순간 `DATABASE_URL`을 검사하고 없으면 던진다.
개발 PC에서는 `.env.local`이 있어 지나가지만, 이미지에는 `.dockerignore`가
`.env*`를 막아 두어(**그게 맞다**) 값이 없다.

**해결** — 빌드 단계에만 누가 봐도 가짜인 값을 넣는다. 접속은 하지 않는다;
값이 있기만 하면 된다. 그 값은 최종 이미지에 남지 않는다(3단계는 별도 `FROM`).

```dockerfile
ENV DATABASE_URL="postgresql://build:build@127.0.0.1:5432/build_time_only"
```

njlee는 `FILE_STORAGE_ROOT`도 함께 필요했다.

> 이것이 **"컨테이너에 올려 보면 내 PC에서만 되던 것이 드러난다"**의 실제 사례다.
> 개발이 다 끝난 뒤에 만났다면 원인을 찾는 데 훨씬 오래 걸렸을 것이다.

### ② `postgresql-client-17`은 한 줄로 깔리지 않는다

Debian bookworm의 기본 저장소에는 **15까지만** 있다. PostgreSQL 공식 저장소를
먼저 추가해야 17이 나온다. Dockerfile에 그 절차가 들어가 있다.

### ③ 옮길 파일은 490MB가 아니라 108MB다

`docker images`가 보여 주는 **490MB는 압축이 풀린 크기**다. `docker save`가
만드는 파일은 훨씬 작다.

| 이미지 | `docker images` | `docker save` 파일 |
|---|---|---|
| `dss-auth:1.0` | 490MB | **108MB** |
| `dss-as:1.0` | 487MB | **107MB** |
| `dss-meters:1.0` | 493MB | **109MB** |
| | | **합계 324MB** |

NAS 공유폴더로 셋을 다 옮겨도 324MB다. 저장·복원에 각각 4초 남짓 걸린다.

**왕복을 실제로 해 봤다.** 저장 → **이미지를 지우고** → 복원 → 검증까지 돌려서,
되살아난 이미지가 `pg_dump 17.11`을 답하고 `server.js`·`public`·`static`을
그대로 갖고 있는 것을 확인했다. 지우지 않고 복원하면 아무것도 증명하지 못한다.

### ④ A/S 이미지에 `src/` 208개 파일이 딸려 왔다 (2.2MB)

`.test.ts`까지 포함돼 있다. Next의 파일 추적기가 넓게 잡은 결과다.
**크기로도 보안으로도 문제는 아니다**(HTTP로 노출되지 않는다). 다만 알아 둔다.

정리하고 싶으면 `next.config.ts`에 한 줄이면 된다.

```ts
outputFileTracingExcludes: { "*": ["src/**/*.test.ts", "src/**/*.test.tsx"] },
```

## 8. 아직 풀지 않은 것 — 컨테이너에서 스크립트를 어떻게 돌리나

> ⚠️ **다음 세션이 이어받을 지점이다.**

`tsx`와 `drizzle-kit`이 세 저장소 모두 **devDependency**다. standalone 이미지에는
개발 의존성이 담기지 않으므로, **이미지 안에서 이 둘이 안 돈다.**

| 명령 | 필요한 것 | 이미지 안에서 |
|---|---|---|
| `npm run backup` | `tsx` + `scripts/` | ❌ 안 됨 |
| `npm run db:migrate` | `drizzle-kit` + `drizzle/` | ❌ 안 됨 |

`pg_dump`는 이미지에 넣었으니 **재료는 있다.** 부를 방법이 없을 뿐이다.

### 생각해 둔 길 셋

| | 방법 | 장점 | 대가 |
|---|---|---|---|
| ㄱ | 실행 이미지에 `scripts/`와 `tsx`를 함께 담는다 | `npm run backup`이 지금과 똑같이 동작 | 이미지가 커지고, 운영에 개발 도구가 들어간다 |
| ㄴ | `builder` 단계를 별도 이미지로도 태그해 일회성 작업에 쓴다 | 운영 이미지는 깨끗하게 유지 | 이미지를 둘 관리 |
| ㄷ | DSM 작업 스케줄러가 호스트에서 `docker exec db pg_dump`를 직접 부른다 | 앱 이미지를 안 건드림 | 사진·키 백업은 따로 처리해야 함 |

**ㄷ만으로는 부족하다.** 백업 스크립트가 DB만 뜨는 게 아니라 계측기 사진을
미러링하고(njlee) 서명 키를 챙기기(dss-auth) 때문이다.

지금 판단으로는 **ㄴ이 가장 깔끔해 보인다** — 운영 이미지를 작고 단순하게 두면서
필요할 때만 도구가 든 이미지를 쓴다. 다만 4단계에서 실제로 백업을 돌려 보기 전에
확정하지 않는다.
