## 2. 🔴 서브모듈 — `git archive` 가 담지 못한다

### 무슨 일인가

오늘 세 사이트(A/S · 계측기 · 개선요청) 전부에 `vendor/dss-ui` **서브모듈**이 생겼다.
`git archive` 는 서브모듈의 **내용을 담지 않는다** — 트리에 적힌 것이 파일이 아니라
커밋 하나이기 때문이다:

```
$ git ls-tree HEAD vendor/
160000 commit c3428e243357a9f862d8f64ead4e954ed0d4ff72    vendor/dss-ui
        ↑ 파일이 아니라 "저 커밋을 여기 붙여라" 라는 표시. archive 는 빈 폴더만 낸다.
```

그대로 구우면 `next build` 가 `@dss/ui` 를 찾지 못한다. 세 저장소의 `tsconfig.json` 이
`"@dss/ui": ["./vendor/dss-ui/src/index.ts"]` 로 **저장소 안의 소스**를 가리키기 때문이다
(npm 의존성이 아니다 — 그래서 `npm ci` 는 멀쩡히 지나가고 `next build` 에서 죽는다).

### 고른 길 — ㄱ. **작업 폴더에서 그대로 굽고, 「커밋된 상태만」은 `git status` 로 보증한다**

| | 길 | 판단 |
|---|---|---|
| **ㄱ** | 작업 폴더에서 그대로 `docker build` | ✅ **채택** |
| ㄴ | `git clone --recursive` 로 임시 작업본을 만들어 거기서 굽는다 | 남겨 둔다 (아래) |
| ㄷ | 서브모듈을 그만두고 파일을 복사해 넣는다 | 안 한다 — 저장소를 나눈 이유가 사라진다 |

**ㄱ 을 고른 근거 — 넷 다 실제로 확인했다.**

1. **`.dockerignore` 넷 중 어느 것도 `vendor/` 를 막지 않는다.** 네 파일을 다 읽어
   확인했다(A/S · 포털 · 계측기 · 개선요청). 그러므로 작업 폴더를 컨텍스트로 주면
   `COPY . .` 가 서브모듈 소스를 그대로 싣는다.
2. `.dockerignore` 의 `.git/` 은 **뿌리 한 곳만** 잡는다. `vendor/dss-ui/.git`(41바이트
   짜리 표시 파일)만 따라 들어가는데, 그 안에는 아무 내용이 없다 — 해가 없다.
3. `@dss/ui` 는 npm 의존성이 아니라 `tsconfig.json` 의 **경로 별칭**이다. 그래서
   `deps` 단계(`package.json`·`package-lock.json` 만 복사 → `npm ci`)는 서브모듈 없이도
   지나간다. 서브모듈이 필요한 자리는 `builder` 단계의 `next build` 하나뿐이고,
   작업 폴더로 구우면 그 자리에 진짜 파일이 있다.
4. ㄴ(임시 클론)이 주는 것은 「커밋된 상태만」이라는 보증 하나인데, 그것은 **굽기 전에
   `git status` 를 보는 것으로 똑같이 얻는다.** 대신 ㄴ 은 네트워크를 요구한다 —
   `.gitmodules` 의 주소가 `https://github.com/kiri190-me/dss-ui.git` 절대 주소라
   로컬 클론만으로는 서브모듈이 채워지지 않는다. 저장소 셋을 클론하고
   `npm ci` 를 캐시 밖에서 다시 도는 값도 붙는다.

> ㄴ 을 버리지는 않는다. **개발 PC 가 아닌 곳에서 굽게 되는 날**(다른 사람 PC · CI)
> 에는 ㄴ 이 맞다. 그때 쓸 명령:
> ```
> git clone --recurse-submodules <저장소 주소> <임시폴더>
> cd <임시폴더> && git checkout <커밋> && git submodule update --init --recursive
> ```

### 🔴 굽기 전 검사 — 세 줄. 하나라도 어긋나면 굽지 않는다

작업 폴더에서 굽는 대가는 「지금 폴더에 있는 것」이 곧 이미지가 된다는 것이다.
그래서 **커밋되지 않은 것이 없다는 사실을 눈으로 본 뒤에만** 굽는다.

```bash
# 저장소마다 (A/S · 계측기 · 개선요청)
cd C:/Users/희만/Desktop/Development/RF_Service_System

git status --porcelain            # ① 아무것도 나오지 않아야 한다 (슈퍼프로젝트)
git -C vendor/dss-ui status --porcelain   # ② 아무것도 나오지 않아야 한다 (서브모듈 안)
git submodule status              # ③ 맨 앞 글자가 '+' 나 '-' 가 아니라 **공백**이어야 한다
#   공백 = 적힌 커밋 그대로   + = 다른 커밋   - = 아예 안 받아졌다(빈 폴더)
git rev-parse HEAD                # ④ 굽는 커밋을 로그에 적어 둔다
```

②를 따로 보는 이유: ①만으로는 설정(`diff.ignoreSubmodules` 등)에 따라
서브모듈 안의 변경이 가려질 수 있다. 두 곳을 각각 본다.

③이 `-` 면 **서브모듈이 빈 폴더다.** `git submodule update --init --recursive` 로 채운 뒤
다시 본다. 🔴 **이 상태로 구우면 빌드가 깨진다.**

### 🔴 구운 뒤 — 「메뉴바가 이미지에 실제로 들어갔나」

빌드가 성공한 것만으로는 부족하다. 개발 PC 에서, **NAS 로 보내기 전에** 본다.

```bash
# 세 앱 이미지 각각 (dss-as:1.5 · dss-meters:1.2 · dss-improvements:0.1)
docker run --rm --entrypoint sh dss-as:1.5 -c \
  "grep -rl 'dss-menu' /app/.next/static /app/.next/server 2>/dev/null | head -5"
```

- **줄이 하나라도 나오면 들어간 것이다.** `dss-menu` 는 `@dss/ui` 의 CSS 클래스
  이름(`.dss-menu` · `dss-menu__dropdown` · `dss-menu__item` …)이라, 스타일시트에도
  서버 번들의 문자열에도 그대로 남는다. 다른 데서 나올 이름이 아니다.
- **아무것도 안 나오면 메뉴바가 없는 이미지다.** 굽기 전 검사 ③으로 돌아간다.

> 왜 `vendor/dss-ui` 폴더를 찾지 않나 — 운영 이미지에는 소스가 없다. 3단계가
> `.next/standalone` · `.next/static` · `public` 만 담기 때문이다. 메뉴바는 **번들 안으로
> 컴파일돼 들어간다.** 그래서 폴더가 아니라 이름을 찾는다.

배포 뒤 화면에서 보는 법은 7-E 에 있다.

### 3-1. 야간 백업이 무엇을 뜨나 (`nas/jobs/backup-nightly.sh`)

DSM 작업 스케줄러 **「DSS 야간 백업」이 매일 02:30 에 root 로** 돌린다.

| 파일 셋 — `meters-files` · `as-attachments` · `auth-keys` | `/volume1/dss/backups/files/<그 이름>/` (`rsync -a`, **지우지 않고 쌓는다**) | 계속 쌓임 |

빈 파일·깨진 파일은 남지 않는다 — `.part` 로 쓰고 `pg_restore -l` 로 열어 본 뒤에만

- 견적서 공유폴더 `/volume1/3_견적-세금계산서-국내발주/…` (직원의 서류함. 백업 대상 밖)

- ⚠️ **같은 디스크 안의 백업이다.** 디스크가 죽으면 함께 죽는다(README ②표 6번).

### 3-2. 배포 직전에 손으로 한 번 더

야간 백업을 그대로 부른다. 같은 파일을 두 번 뜨는 것이 아니라 **새 시각의 백업이
하나 더 생긴다**(개수 정리는 30개 기준이라 옛 것을 밀어내지 않는다).

```bash
# (PowerShell) ssh dss-nas
# (NAS)        sudo -i          ← DSM 비밀번호. 한/영이 영문인지 먼저 확인
bash /volume1/dss/jobs/backup-nightly.sh
echo "종료 코드: $?"            # 🔴 0 이 아니면 여기서 멈춘다. 배포를 시작하지 않는다
ls -lt /volume1/dss/backups/db/ | head -6
```

통과 기준: 마지막 줄이 `── 성공`, `dss_as`·`dss_auth`·`dss_meters` 세 줄에 `✓` 와
표 개수가 찍혀 있을 것.

> 🔴 **이것은 되돌리기 지점이 아니다.** 되돌리기 지점은 **앱을 멈춘 뒤에** 뜨는 덤프다
> (`05-배포-리허설.md` 8절 ③ — 「덤프와 전환 사이에 들어온 자료는 사라진다」).
> 이 백업의 역할은 **덤프가 실패했을 때 돌아갈 자리**와, 아래 3-3 을 안전하게 하는 것이다.

### 3-3. 🔴 0104 전용 — 개선요청 자료를 **읽을 수 있는 꼴로** 따로 뽑는다

0104 는 `improvement_requests` 표를 **통째로 지운다**(`DROP TABLE … CASCADE`). 그
표와 첨부 기록은 `pg_dump -Fc` 안에 들어 있지만, **칸이 사라진 뒤에는 그대로
되돌려 넣을 수 없다** — `attachments.improvement_request_id` 가 없어지기 때문이다.
그러므로 이 자료는 「되돌려 쓰는 것」이 아니라 **「읽어서 새 사이트에 다시 적는 것」**이다.

```bash
# (NAS · 사람 · sudo -i)
S=$(date +%Y%m%d-%H%M%S); B=/volume1/dss/backups/improvements-before-0104-$S
mkdir -p "$B"; chown root:root "$B"; chmod 700 "$B"

# ① 몇 건인지 먼저 센다 — 0 이면 이 절은 건너뛴다
/usr/local/bin/docker exec dss-pg-app sh -c \
  'psql -U "$POSTGRES_USER" -d dss_as -Atc "select count(*) from improvement_requests"'
/usr/local/bin/docker exec dss-pg-app sh -c \
  'psql -U "$POSTGRES_USER" -d dss_as -Atc "select count(*) from attachments where improvement_request_id is not null"'

# ② 표 둘을 되살릴 수 있는 꼴로
/usr/local/bin/docker exec dss-pg-app sh -c \
  'pg_dump -U "$POSTGRES_USER" -d dss_as -Fc -t improvement_requests' > "$B/improvement_requests.dump"

# ③ 사람이 읽는 꼴로 (새 사이트에 다시 적을 때 이것을 본다)
/usr/local/bin/docker exec dss-pg-app sh -c \
  'psql -U "$POSTGRES_USER" -d dss_as -c "\copy (select * from improvement_requests order by created_at) to stdout csv header"' \
  > "$B/improvement_requests.csv"
/usr/local/bin/docker exec dss-pg-app sh -c \
  'psql -U "$POSTGRES_USER" -d dss_as -c "\copy (select id, improvement_request_id, file_name, stored_path, category, created_at from attachments where improvement_request_id is not null) to stdout csv header"' \
  > "$B/improvement_attachments.csv"

ls -l "$B"
```

**첨부 파일(바이트)은 지워지지 않는다** — 디스크에 그대로 남고, 야간 백업도
`--delete` 없이 쌓기만 하므로 사본도 남는다. 사라지는 것은 **그 파일을 가리키던 DB 줄**
이다. `improvement_attachments.csv` 의 `stored_path` 가 그 파일을 다시 찾는 열쇠다.

> ⚠️ 개발 PC 에서 같은 일을 할 때 나온 수는 **본문 10건 · 첨부 2건**이었다
> (`RF_Service_System/HANDOFF.md` B절). **운영의 수는 다르다 — ①로 직접 센다.**

### 3-4. 되돌릴 때 어떻게 쓰나

| 상황 | 쓰는 것 | 명령 |
|---|---|---|
| 정지 창 안에서 A/S 를 되돌린다 | **앱을 멈춘 뒤 뜬 `pre-deploy-<시각>/dss_as.dump`** | `docker exec -i dss-pg-app sh -c 'pg_restore -U "$POSTGRES_USER" -d dss_as --clean --if-exists --no-owner' < <파일>` |
| 그 덤프가 없거나 깨졌다 | 3-2 의 야간 백업 `/volume1/dss/backups/db/dss_as_<시각>.dump` | 같은 명령. 🔴 **그 시각 이후의 자료는 사라진다** |
| 개선요청 본문을 다시 보고 싶다 | 3-3 의 `improvement_requests.csv` | 읽어서 새 사이트에 사람이 적는다 |
| 첨부 파일을 찾고 싶다 | `improvement_attachments.csv` 의 `stored_path` | `/volume1/dss/as-attachments/<그 경로>` |

되돌리기 전체 표는 [`05-배포-리허설.md`](./05-배포-리허설.md) **9절**에 있다.

## 4. 마이그레이션 0100 ~ 0105 — 무엇을 하고, 무엇이 되돌아오지 않나

개발 DB 에는 여섯 다 적용돼 있고(0100·0101 은 시험 DB 에도), **운영에는 하나도 없다.**
NAS 의 파일 수는 `100` 건에서 **`106` 건**이 된다(`0000`~`0105`).

| | 무엇을 하나 | 되돌리기 |
|---|---|---|
| **0100** | 작업비를 세 몫으로. `repair_labor_settings` 에 `investigation_hours`·`document_hours`, `power_test_tasks.scope`(enum 신설), `quotes.document_excluded`. 🔴 **손으로 더한 UPDATE 가 기존 값을 옮긴다** | 🔴 **태그만으로는 안 된다.** `scope` 가 NOT NULL·기본값 없음이라 옛 코드가 통전 건명을 넣지 못한다. 옛 유니크 인덱스 하나를 `DROP` 한다(되살리려면 손으로) |
| **0101** | 케이블 견적서. `quote_items.kind`·`part_spec_text`, `quotes.remarks`, CHECK 넷을 좁혀 다시 검 | 🔴 **`ALTER TYPE quote_kind ADD VALUE 'CABLE'` — PostgreSQL 은 enum 값을 지우지 못한다.** 나머지는 더하기 |
| **0102** | 표 `repair_case_used_parts` 신설 (사용 부품) | **더하기만.** 옛 코드는 그 표를 모른 채 돈다 |
| **0103** | 부품 단가에서 소유구분을 없앤다 | 🔴 **되돌릴 수 없다.** 같은 부품의 여러 줄을 **DELETE** 로 합치고(비싼 쪽을 남긴다) `owner` 칸을 `DROP` 한다. 개발에서는 5행 → 3행이었다 — **운영의 수는 다르다** |
| **0104** | 🔴 **개선요청을 A/S 에서 완전히 지운다.** `DELETE FROM attachments WHERE improvement_request_id IS NOT NULL` → `DROP TABLE improvement_requests CASCADE` → 칸·FK·색인·CHECK·`DROP TYPE` | 🔴🔴 **이 배포에서 가장 위험한 한 줄.** 되돌릴 수 없다. **3-3 을 먼저 하지 않으면 운영 자료가 사라진다** |
| **0105** | 견적서 결재 바탕. 표 `quote_approvals` 신설, `quote_approval_status` enum 신설 | 표는 더하기. 🔴 **`ALTER TYPE shipment_approval_route_scope ADD VALUE 'QUOTE'` 는 지우지 못한다** |

**정리 — 되돌릴 수 없는 것 넷:** `0101`·`0105` 의 **enum 값 추가 둘**,
`0103` 의 **DELETE + DROP COLUMN**, `0104` 의 **DROP TABLE + DELETE**.
그래서 이 배포의 되돌리기는 [`05`](./05-배포-리허설.md) 9절 표의 **「다」 줄**이다 —
*정지 창 안에서* 덤프로 되돌리는 것만이 길이고, **다음 날 발견하면 「라」(사실상 불가)**가 된다.

### 🔴 0100 적용 뒤 — 반드시 본다

```bash
/usr/local/bin/docker exec dss-pg-app sh -c 'psql -U "$POSTGRES_USER" -d dss_as -c \
 "select equipment_kind, base_cost, power_test_hours, investigation_hours, document_hours from repair_labor_settings order by equipment_kind"'
```

- `investigation_hours` 가 **NULL 인 줄이 있으면 그 장비의 기본 작업비가 0 이 된다.**
  값이 정수로 떨어지지 않거나 통전 몫이 기본 작업비 이상일 때 그렇게 남는다(적용은 성공한다).
- **사람이 A/S 화면(작업 비용 설정)에서 채워야 한다.** 채우기 전까지 그 장비의
  견적서 금액이 틀린다.
- `document_hours` 는 **전부 NULL 인 것이 맞다** — 새 개념이라 정해진 값이 없다.
- 참고로 개발 DB 에서는 GENERATOR 21 · MATCHER 21 · T/C 22 가 되었고 **청구 금액이
  그대로였다.** 🔴 **운영 값은 다를 수 있다** — 바꾸기 전 표와 바꾼 뒤 표를 둘 다 로그에 남긴다.

## 5. 계측기 브랜치 — ✅ **`main` 으로 정해졌다** (2026-09-18)

**사용자가 아래 「나」를 골랐고, 이미 실행됐다.** 계측기는 **`main` 에서 굽는다.**
7-A 의 계측기 줄도 그렇게 적혀 있다.

### 지금 상태 (병합 뒤 확인한 것)

| | |
|---|---|
| 한 일 | `sso-integration` 을 `main` 으로 **fast-forward 병합**했다 — `main` 이 `6879ff6` → **`c6aec54`**(15커밋). `origin/main` 에 푸시까지 끝났다 |
| 두 브랜치 | **같은 커밋을 가리킨다** — `git rev-list --left-right --count main...sso-integration` → **`0  0`** |
| `main` 의 내용 | `Dockerfile` 도 `.gitmodules` 도 **있다**(`git cat-file -e main:…` 통과). `git ls-tree main vendor/` → `160000 commit c3428e2…` — 1절 표의 서브모듈 커밋과 같다 |
| 🔴 `sso-integration` 브랜치 | **아직 지우지 않았다** — 로컬·원격 둘 다 남아 있다. 지울지는 이 배포와 별개로 정한다 |
| 🔴 `upstream` 과의 관계 | 이 병합으로 우리 `main` 이 **`upstream/main`(이남준 님 원본 `skawnszz-creator/njlee`)보다 15커밋 앞선다.** 그전에는 같은 커밋이었다. upstream 은 `no_push` 로 막아 두었으므로 이쪽에서 밀려 올라갈 일은 없다. **되돌려 보낼 생각이 있는지는 여전히 열린 물음이다** |
| 저장소 사정 | `origin` = `kiri190-me/dss-meters`(우리 것), `upstream` = `skawnszz-creator/njlee`(이남준 님) |

### 왜 그렇게 정했나 — 판단 재료 (병합 전에 적은 것)

**어느 쪽을 고르든 굽는 커밋은 `c6aec54` 로 같고, 화면 결과도 같았다.**
그래서 진짜 물음은 「어느 브랜치를 굽나」가 아니라
**`sso-integration` 을 `main` 으로 합칠 것인가**였다.

| | 고르면 | 얻는 것 | 대가 |
|---|---|---|---|
| **가** | 그대로 `sso-integration` 에서 굽고 브랜치를 둔다 | 배포일에 할 일이 없다. 그때까지와 같다 | `main` 이 계속 운영과 다르다. 클론하는 사람이 틀린 브랜치를 집는다 |
| **나** ✅ | 배포 전에 `main` 으로 fast-forward 병합하고 `main` 에서 굽는다 | 네 저장소가 같은 모양이 된다. 「어느 브랜치냐」를 다시 묻지 않는다 | `upstream`(이남준 님 원본)과의 관계를 바꾼다 |

**「나」가 싼 이유** — 병합이 **fast-forward** 였다. 병합 전 `main` 에만 있는 커밋이
**0** 이라(`0  15`) `sso-integration` 이 `main` 의 상위집합이었고, 되돌리기도
`main` 을 `6879ff6` 로 되감으면 끝이다. 파일 차이는 52개 · +3,516 / −380
(`vendor/dss-ui` 포함)였지만 **그 전부가 이미 운영에서 도는 코드**다.

### 🔴 남겨 두는 사실 — 한때는 이랬다

- **지금 운영에 도는 `dss-meters:1.1` 은 `sso-integration` 에서 구운 것이다.**
  병합 전 `main` 에는 `Dockerfile` 도 `.gitmodules` 도 **없었다**(`git cat-file -e
  main:Dockerfile` 이 실패했다). 그래서 클론하는 사람이 틀린 브랜치를 집지 않도록
  README 「인계 메모」에 경고 줄이 있었다 — 지금은 해소로 고쳐 두었다.
- 병합 전에는 **`main` 을 굽는 것이 사실상 선택지가 아니었다.** SSO 연결(`de2ec73`)과
  로그인 화면 제거(`3b9da29`)가 둘 다 브랜치에만 있어, `main` 을 구우면 로그인이
  달라졌다. 병합이 그 둘을 `main` 으로 들여왔다.

## 6. 배포 순서와 근거

```
① 백업 (3절)                     ← 무엇보다 먼저. 실패하면 여기서 끝낸다
② 포털  dss-auth 1.3 → 1.4        ← 🔴 이것이 가야 메뉴바가 뜬다
③ A/S   dss-as 1.4 → 1.5 + 마이그레이션 0100~0105
④ 계측기 dss-meters 1.1 → 1.2
⑤ 개선요청 첫 설치 (runbook/06)   ← 🔴 따로 날을 잡아도 된다. 9절
```

**왜 포털이 먼저인가.** 메뉴바가 그릴 목록은 포털이 **ID 토큰의 `dss_services`
클레임**으로 내준다(`59deacf`). 받는 쪽(A/S·계측기·개선요청)은 그 값을 서명 쿠키에
옮겨 담을 뿐 스스로 만들지 않는다. 포털이 옛 이미지면 클레임이 없고, 그러면
**세 사이트는 메뉴바를 아예 그리지 않는다** — 빈 띠도 그리지 않는다
(`RF_Service_System/src/lib/auth/service-menu-cookie.ts` 가 그렇게 만들어져 있다).

**반대로 해도 깨지지는 않는다.** A/S 를 먼저 올려도 로그인은 예전과 똑같이 되고
메뉴만 안 보인다. 다만 **직원이 다시 로그인해야** 메뉴가 나타난다 — 토큰은 로그인할
때만 나가기 때문이다(그 커밋의 「남는 한계」). 순서를 지키면 그 한 번이 줄어든다.

**A/S 가 계측기보다 먼저인 이유** — A/S 만 마이그레이션이 있고 유일하게 되돌리기가
어렵다. 정지 창의 시간을 거기에 몰아 주고, 계측기는 태그만 바꾸면 끝나는 일로 남긴다.

**포털과 A/S 는 같은 정지 창 안에서** 한다(둘 다 멈춘다). 계측기는 그 뒤에 따로
띄워도 되고 같은 창 안에서 해도 된다 — 마이그레이션이 없어 되돌리기가 1분이다.

## 8. 잘못됐을 때 되돌린다

전체 표는 [`05-배포-리허설.md`](./05-배포-리허설.md) **9절**. 이번 배포에 해당하는 줄만:

| | 무엇을 | 어떻게 | 잃는 것 |
|---|---|---|---|
| 포털 | 이미지만 | compose 태그 `dss-auth:1.4` → `1.3` → `up -d --no-deps app-auth` | 없음 (마이그레이션 없음) |
| 계측기 | 이미지만 | 태그 `1.2` → `1.1` → `up -d --no-deps app-meters` | 없음 |
| 개선요청 | 앱만 내린다 | `$C stop app-improvements && $C rm -f app-improvements` | 없음 (런북 06 6절) |
| **A/S** | 🔴 **이미지 + DB 둘 다** | `stop app-as` → `pre-deploy-<시각>/dss_as.dump` 복원 → 첨부 스냅숏 되돌림 → 태그 `1.5` → `1.4` → `up -d` | **정지 창 안이면 없다.** 창을 넘기면 그 뒤의 자료 전부 |

🔴 **A/S 는 「태그만 되돌리기」가 통하지 않는다.** `power_test_tasks.scope` 가
NOT NULL·기본값 없음이라 옛 이미지가 통전 건명을 넣지 못하고, 0103·0104 가 지운 것은
스키마에서 아예 사라졌다. **덤프 복원이 유일한 길이다.**

🔴 **되돌릴지 말지는 정지 창 안에서 정한다.** 스모크를 통과하지 못하면 **무조건**
되돌린다. *「조금만 더 보면 될 것 같다」가 가장 비싼 판단이다* — 그렇게 창을 넘기면
「다」가 「라」(사실상 불가)로 바뀐다.

## 9. 개선요청 — 같은 날인가, 다른 날인가

**절차는 이 문서에 다시 적지 않는다.** [`06-개선요청-배포.md`](./06-개선요청-배포.md)
한 곳에 다 있다 — 이 문서는 **언제 할지**만 정한다.

| | 같은 날에 | 🔴 따로 날을 잡는다 (권한다) |
|---|---|---|
| 얻는 것 | 메뉴바에 네 시스템이 처음부터 다 뜬다 | 정지 창이 짧아지고, 문제가 생겼을 때 원인이 하나다 |
| 대가 | 🔴 **사람이 손으로 하는 일이 일곱 더 붙는다**(런북 06 2절 — 비밀번호 · 롤·DB · 폴더 권한 · 포털 등록 · Cloudflare · 프록시 · env 파일). 그중 **DNS 반영과 포털 등록은 시간이 걸리고 되돌리기가 번거롭다** | 그날까지 A/S·계측기의 메뉴에 **개선요청이 안 보인다**(포털 `clients` 에 없으므로) |

> 🔴 **개선요청이 메뉴에 뜨려면 포털 `clients` 등록이 먼저다** — 런북 06 의 2-ㄹ.
> 사이트를 띄우는 것과 메뉴에 보이는 것은 다른 일이다.

**따로 하기로 하면** 개선요청 배포는 런북 06 만 보고 진행하고, 이 문서의 ②~④가 끝난
뒤 아무 날에나 해도 된다 — 그 사이 세 사이트는 **시스템 셋짜리 메뉴**를 보여 준다.

## 11. 🔴 확인이 필요한 것 — 단정하지 않았다

배포하는 사람이 **현장에서 직접 봐야 하는 것들**이다. 여기 적힌 것을 「확인했다」로 읽지 말 것.

1. **운영 A/S 에 개선요청 자료가 몇 건 있는지 모른다.** 개발 PC 에서는 10건이었지만
   운영은 다른 DB 다. **3-3 ①로 직접 센다.** 0 이면 0104 의 무게가 크게 줄어든다.
2. **케이블 견적서 양식의 실제 파일 이름을 모른다.** `.env.example` 은 값을 비워 두었고
   실제 경로는 `.env.local` 에만 있다(출력 금지). `/volume1/dss/as-templates` 에 무엇이
   들어 있는지 NAS 에서 보고 정해야 한다.
3. **매쳐 양식 파일 둘이 NAS 에 실제로 있는지 확인하지 않았다.** compose 에는 경로가
   적혀 있지만(`/templates/매쳐 내자 견적서.xlsx` · `매쳐 OH 견적서.xlsx`), 파일이 있는지는
   NAS 에서 `ls` 로 봐야 안다. **하나라도 못 읽으면 그 출력이 통째로 죽는다.**
4. **`nas/env/as.env` 와 NAS 의 것이 갈라져 있다 — 🔴 배포와 섞지 말고 따로 할 일이다.**
   이 PC 사본은 **2026-09-15 것**이고, NAS 것에는 그 뒤 배포(08·09)에서 더한
   `QUOTE_ARCHIVE_DIR` · `QUOTE_ARCHIVE_UNC_ROOT` · `QUOTE_ARCHIVE_UNC_ROOT_ALT` 가 있다
   (`nas/setup/07~09-deploy.sh` 가 그 줄들의 존재를 검사한다). **이번 배포에서는 올리지
   않으므로 위험이 없다**(10절 3번) — 갈라진 것은 그대로 둔다. 언젠가 맞출 때는
   **NAS 것을 정본으로 받아** 이 PC 사본을 고치는 방향이다. 반대로 하면 운영에서
   줄이 사라진다. 🔴 맞출 때도 **값은 출력하지 않는다** — 항목 이름과 해시로만 비교한다.
5. **A/S·계측기 도구 이미지가 `vendor/` 를 복사하지 않는다.** 지금 부르는 스크립트들은
   화면 조각을 불러오지 않으므로 괜찮아 **보인다** — 그러나 실제로 돌려 확인하지 않았다.
   도구 이미지를 다시 굽게 되면 그때 반드시 시험한다.
6. **`02-이미지-빌드.md` 8절의 「길 ㄴ」은 A/S·계측기에만 닫혀 있다.** 개선요청은
   도구 이미지 안에 `drizzle/` 을 굽는 방식이라, **마이그레이션이 늘 때마다 도구
   이미지를 다시 구워야 한다**(런북 06 3절).
7. **백업을 되살려 본 적이 없다**(README ②표 13번). 이 문서의 8절은 **해 보지 않은
   절차**다. 되돌릴 일이 실제로 생기면 그 자리에서 처음 해 보는 것이 된다.
8. **견적서 공유폴더와 `as-templates` 는 야간 백업 밖이다.** DSM 쪽에 별도 백업이
   걸려 있는지 확인하지 않았다.
9. **정지 시간을 짐작으로 적었다.** 지난 배포(`07-deploy.sh`)에서 **51초**였지만
   이번에는 마이그레이션이 여섯이고 그중 둘이 자료를 옮긴다. **창은 30분 잡는다.**
