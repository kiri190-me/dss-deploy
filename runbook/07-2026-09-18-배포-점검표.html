손대지 않는다env/*.env 를 올리지 않는다

이번 배포에 새 환경변수가 하나도 없습니다. 확인했습니다 — 견적서 결재는 새 변수가 없고, 메뉴바가 쓰는 AUTH_SESSION_SECRET 은 이미 있습니다. 케이블 양식 경로는 compose 에 넣습니다(4번).

이 PC 의 as.env 는 9월 15일 것이라 NAS 에 있는 세 줄이 없습니다 — QUOTE_ARCHIVE_DIR · QUOTE_ARCHIVE_UNC_ROOT · QUOTE_ARCHIVE_UNC_ROOT_ALT. 올리면 그 셋이 운영에서 사라집니다. 손대지 않으면 NAS 것이 그대로 남습니다.

배포 스크립트가 그 셋의 존재뿐 아니라 값의 형태까지 검사합니다 — UNC_ROOT 가 IP 인지, _ALT 가 이름인지. 9월 16일에 그 차례를 바꾼 기록이 있습니다.

로컬 사본이 NAS 와 갈라져 있다는 사실 자체는 언젠가 맞춰야 합니다 — 배포와 섞지 말고 따로 하세요.

끝남NAS 의 양식 여섯을 확인했다 9/18

여섯 개가 다 있고 compose 에 적힌 경로와 파일명이 글자 하나까지 맞습니다. 권한도 정확합니다 — -r--------, 소유자 1000:1000.

내자견적서.xlsxQUOTE_TEMPLATE_PATH
제너레이터 OH 견적서.xlsxOH_QUOTE_TEMPLATE_PATH
매쳐 내자 견적서.xlsxMATCHER_QUOTE_TEMPLATE_PATH
매쳐 OH 견적서.xlsxMATCHER_OH_QUOTE_TEMPLATE_PATH
검사보고서.xlsxINSPECTION_REPORT_TEMPLATE_PATH
수리보고서.xlsxREPAIR_REPORT_TEMPLATE_PATH

다시 볼 일이 있으면 sudo ls -l /volume1/dss/as-templates/ — 🔴 sudo 없이는 Permission denied 입니다. 이 폴더는 auth-keys 와 같은 등급(500/400)으로 잠겨 있습니다. 직인과 계좌가 든 양식이라 앱만 읽고 아무도 쓰지 못하게 해 두었습니다.

끝남케이블 양식을 NAS 에 올렸다 9/18

지문을 대조해 깨지지 않은 것을 확인했고, 권한도 다른 여섯과 같게 맞췄습니다.

-r-------- 1 1000 1000  50996  '케이블 견적서.xlsx'
sha256  7bfc64e9…  (개발 PC 원본과 일치)

겪은 함정 둘 — ① 보내는 명령은 개발 PC 에서 돌립니다(NAS 에는 C: 가 없습니다). PowerShell 은 < 를 지원하지 않아 cmd /c 로 감싸야 합니다. ② 갓 올라온 파일에는 Synology ACL(+)이 붙어 chmod 를 눌러 이깁니다 — /usr/syno/bin/synoacltool -del 로 먼저 걷어야 합니다.

끝남compose 에 케이블 경로를 넣었다 9/18

견적서 넷 뒤·보고서 둘 앞에 넣고 커밋했습니다(f2cc6e8). YAML 을 파싱해 양식 경로 일곱이 다 잡히는 것을 확인했습니다.

CABLE_QUOTE_TEMPLATE_PATH: "/templates/케이블 견적서.xlsx"

🔴 덤: 첫 설치 스크립트(01-prepare.sh)가 아직 「양식이 정확히 6개」인지 검사합니다. 이제 일곱이라 그 검사가 깨집니다 — 이번 배포에는 영향이 없지만(첫 설치용이라 안 돌립니다), 다시 돌릴 일이 생기면 기대값을 7로 고쳐야 합니다. compose 주석에도 적어 뒀습니다.

먼저NAS 의 compose 가 우리 것과 갈라졌는지 본다

보내기 전에 NAS 것을 받아서 견줍니다. as.env 가 그랬듯 NAS 쪽에만 있는 줄이 있으면, 우리 사본을 덮어쓸 때 그게 조용히 사라집니다.

# 우리 것과 견준다
git diff --no-index nas-compose-now.yml dss-deploy\nas\docker-compose.nas.yml
나와야 하는 차이만 나오면 넘어갑니다 — 이미지 태그 셋(1.3→1.4 · 1.4→1.5 · 1.1→1.2), CABLE_QUOTE_TEMPLATE_PATH 한 줄, 개선요청 자리 셋이 주석으로 덮인 것.
그 밖의 차이가 나오면 멈추고 알려 주세요. NAS 에만 있는 줄이면 우리 사본에 먼저 옮겨 담아야 합니다. 스크립트가 옛것을 backups/ 에 넣어 두긴 하지만, 되돌리는 것보다 안 잃는 게 낫습니다.

잊기 쉬움배포 스크립트와 compose 를 보낸다

이 둘을 안 보내면 1단계 검사에서 멈춥니다 — 케이블 견적서 경로(CABLE_QUOTE_TEMPLATE_PATH)가 우리 사본에만 있기 때문입니다.

cmd /c "ssh dss-nas ""cat > /volume1/dss/setup/incoming/docker-compose.nas.yml"" < dss-deploy\nas\docker-compose.nas.yml"

# 보내자마자 잠급니다
ssh dss-nas "chmod 600 /volume1/dss/setup/incoming/docker-compose.nas.yml"
setup/incoming/ 은 777 폴더입니다 — 옮겨지기 전까지 누구나 읽습니다. 보내자마자 chmod 600 하세요.

스크립트가 incoming/docker-compose.nas.yml 을 보면 문법을 먼저 검사한 뒤 옛것을 backups/ 로 옮기고 갈아 끼웁니다. 문법이 틀리면 바꾸지 않고 멈춥니다.

종료 코드가 0 이 아니면 여기서 멈춥니다. 배포를 시작하지 않습니다.

이것은 되돌리기 지점이 아닙니다. 되돌리기 지점은 앱을 멈춘 뒤 뜨는 덤프입니다.

0104 전용개선요청 자료를 읽을 수 있는 꼴로 뽑는다

0104 는 improvement_requests 표를 통째로 지웁니다. 덤프 안에는 있지만 칸이 사라진 뒤에는 그대로 되돌려 넣을 수 없습니다 — 「읽어서 새 사이트에 다시 적는 것」입니다.

S=$(date +%Y%m%d-%H%M%S); B=/volume1/dss/backups/improvements-before-0104-$S
mkdir -p "$B"; chown root:root "$B"; chmod 700 "$B"

# ① 몇 건인지 센다 — 0 이면 이 항목은 건너뛴다
/usr/local/bin/docker exec dss-pg-app sh -c \
  'psql -U "$POSTGRES_USER" -d dss_as -Atc "select count(*) from improvement_requests"'

# ② 되살릴 수 있는 꼴
/usr/local/bin/docker exec dss-pg-app sh -c \
  'pg_dump -U "$POSTGRES_USER" -d dss_as -Fc -t improvement_requests' > "$B/improvement_requests.dump"

# ③ 사람이 읽는 꼴 — 새 사이트에 다시 적을 때 이것을 본다
/usr/local/bin/docker exec dss-pg-app sh -c \
  'psql -U "$POSTGRES_USER" -d dss_as -c "\copy (select * from improvement_requests order by created_at) to stdout csv header"' \
  > "$B/improvement_requests.csv"

첨부 파일의 바이트는 안 지워집니다 — 사라지는 건 그 파일을 가리키던 DB 줄입니다. CSV 의 stored_path 가 파일을 다시 찾는 열쇠입니다.

정지 창 — 포털 + A/S

NAS · 30분

뼈대는 runbook/05 8절 ①~⑪ 그대로입니다. 이번에 달라지는 것만 아래에 적습니다.

먼저바꾸기 전 값을 찍어 로그에 남긴다

0100 과 0103 이 값을 건드립니다. 바꾸기 전 표를 남겨야 나중에 견줄 수 있습니다.

repair_labor_settings 와 part_unit_prices. 07-deploy.sh 의 3·6단계가 그 틀입니다.

포털과 A/S 를 멈춘다

app-auth 와 app-as 둘만. DB 와 계측기는 끄지 않습니다.

되돌리기 지점덤프를 뜬다

dss_as 와 dss_auth 둘 다. 그리고 첨부 스냅숏(cp -al — 하드링크라 즉시·공간 0).

이것이 유일한 되돌리기 지점입니다. 이 덤프와 전환 사이에 들어온 자료는 사라집니다.

이미지를 싣고 지문을 맞춘다

tar 셋을 docker load 하고, 1단계 지문 표의 image ID 와 NAS 의 .Id 를 대조합니다. 스크립트가 알아서 하고, 어긋나면 앱이 살아 있는 채로 멈춥니다.

예정된 경고preflight 가 「되돌리기 불가」를 보고한다

0103 의 DELETE·DROP COLUMN, 0104 의 DROP TABLE 때문입니다. 예정된 것이므로 멈추지 않습니다.

대신 3단계의 자료 뽑기를 했는지 여기서 다시 확인하세요.

마이그레이션을 적용한다

tools-as 로 db:migrate.

끝나면 drizzle.__drizzle_migrations 가 106 이어야 합니다.

반드시0100 적용 뒤 NULL 을 본다

/usr/local/bin/docker exec dss-pg-app sh -c 'psql -U "$POSTGRES_USER" -d dss_as -c \
 "select equipment_kind, base_cost, power_test_hours, investigation_hours, document_hours \
  from repair_labor_settings order by equipment_kind"'
investigation_hours 가 NULL 인 줄이 있으면 그 장비의 기본 작업비가 0 이 됩니다. 7단계에서 화면으로 채워야 합니다.

document_hours 는 전부 NULL 인 것이 맞습니다 — 새 개념이라 정해진 값이 없습니다.

주의태그를 올리고 띄운다

$C up -d --no-deps app-auth app-as
인자 없이 up -d 를 부르지 마세요. 설정 지문이 바뀐 DB 컨테이너까지 다시 만듭니다.

6

확인 — 이 순서로

NAS · 브라우저

컨테이너가 대답하는지

curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:13100/   # ·13000 ·13300
2xx 또는 3xx.

docker ps 에 보이는 것과 대답하는 것은 다릅니다. 대답할 때까지 기다린 시각이 곧 「멈춘 시간」의 끝입니다.

포트가 새지 않았는지 · 밖에서 닿는지

netstat -tln | grep 13

127.0.0.1 의 13000·13100·13300 만 보여야 합니다. 그리고 브라우저로 login·as·meters.dss21.co.kr.

핵심메뉴바가 보이는지

A/S 에 로그인해서 머리말을 봅니다. 드롭다운 단추 하나가 보이고, 누르면 쓸 수 있는 시스템 목록이 펼쳐지고, 바깥을 누르거나 Esc 로 접혀야 합니다.

안 보이면① 포털이 정말 1.4 인가 ② 로그아웃했다 다시 로그인했나 ③ 1단계의 이미지 검사

목록은 로그인할 때만 토큰에 실려 나옵니다. 이미 로그인해 둔 사람은 다시 로그인해야 보입니다.

견적서 결재가 들어갔는지

견적서 화면에 [견적서 결재] 탭이 있고, 사용자 관리 → 승인 절차에 「견적서 승인」 용도가 보이면 0105 가 들어간 것입니다.

남의 것이 안 흔들렸는지

계측기와 포털 화면이 평소대로인지.

배포 뒤에 할 일

며칠 안

빠뜨리면 금액이 틀립니다작업 비용의 빈 칸을 채운다

4단계에서 investigation_hours 가 NULL 로 남은 장비가 있으면, A/S 화면(작업 비용 설정)에서 사람이 채웁니다.

채우기 전까지 그 장비의 견적서 금액이 틀립니다.

포털 「업데이트 소식」을 고친다

A/S 번호가 1.3 으로 하나 낮게 적혀 있습니다. 이번에 1.5 항목과 함께 고칩니다.

package.json 의 version 과 RELEASES 맨 앞 번호를 같이 올려야 시험이 통과합니다.

[폴더 열기] 도우미를 다시 설치한다

값이 바뀌면 PC 마다 다시 설치해야 합니다.

README 를 갱신한다

dss-deploy/README.md 의 「지금 어디까지 됐나」에 이 배포를 적고 단계 표의 태그를 고칩니다.

다음 세션이 그 표로 이어받습니다.

8

개선요청 — 다른 날에

따로 잡기를 권함

절차는 runbook/06-개선요청-배포.md 에 전부 있습니다. 여기서는 언제 할지만 정합니다.

결정같은 날인가, 다른 날인가

같은 날메뉴바에 네 시스템이 처음부터 다 뜬다. 대신 사람 손 일곱이 더 붙고 DNS·포털 등록은 시간이 걸린다
다른 날정지 창이 짧고 문제 원인이 하나다. 대신 그날까지 메뉴에 개선요청이 안 보인다

개선요청이 메뉴에 뜨려면 포털에 사이트를 등록하는 것이 먼저입니다. 띄우는 것과 메뉴에 보이는 건 다른 일입니다.

띄운 뒤 — 야간 백업에 더한다

dss_improvements 와 improvements-uploads 를 backup-nightly.sh 에 넣고 03-install-backup.sh 로 다시 설치합니다.

안 하면 개선요청 자료가 한 번도 백업되지 않습니다.

잘못됐을 때

  1. 스모크를 통과하지 못하면 무조건 되돌립니다. 「조금만 더 보면 될 것 같다」가 가장 비싼 판단입니다.
  2. 포털·계측기·개선요청은 태그만 되돌리면 끝입니다(마이그레이션이 없습니다).
  3. 🔴 A/S 는 태그만으로 안 됩니다. 덤프 복원이 유일한 길입니다 — 4단계에서 뜬 pre-deploy 덤프를 씁니다.
  4. 🔴 정지 창을 넘기면 사실상 되돌릴 수 없습니다. 되돌릴지 말지는 창 안에서 정하세요.
  5. 되돌리기 전체 표는 runbook/05 9절에 있습니다. 다만 백업을 되살려 본 적은 한 번도 없습니다 — 실제로 쓰면 그 자리에서 처음 해 보는 것이 됩니다.
