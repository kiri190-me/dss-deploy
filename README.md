# NAS 이식 — 전체 지도

사내 시스템 넷을 개발 PC에서 **Synology DS218+ NAS의 Docker**로 옮긴다.
이 파일이 전체 순서와 **지금 어디까지 왔는지**를 갖는다. 세션을 이어받으면 여기부터 읽는다.

시스템 경로·포트·확정된 결정은 [CLAUDE.md](./CLAUDE.md)에 있다.

네 질문 중 셋이 닫혔고, 새 문서 [`runbook/03-원격-접속.md`](./runbook/03-원격-접속.md)에 담았다.

- ✅ 밖에서 쓸 사람 **3~5명**
- ✅ **계측기도 밖에서 쓴다** — 셋 다 VPN으로
- ✅ **공유기가 두 대다** — 바깥 **ipTIME A2004NS-MU**(인터넷 직결), 안쪽 **ASUS RT-AC58U**
- ⬜ 회선 **업로드 속도** — 측정법은 런북 03의 4절 ㄹ
- ⬜ **두 공유기가 어떻게 이어져 있나** (AP 모드인가 · NAS는 어디 물려 있나) — 런북 03의 3절 ㄹ

**여기서 방향이 바뀌었다.** 앞서 *"공유기가 지원하면 NAS 부담 없이 가장 깔끔하다"*고
적었는데, **여기 있는 두 대는 그 전제에 맞지 않는다.**

| | 사정 |
|---|---|
| ipTIME A2004NS-MU (바깥) | ipTIME이 WireGuard를 넣은 펌웨어 **14.20.0의 지원 모델 목록에 없다**(목록은 A3004부터 위). ipTIME은 OpenVPN 서버를 하지 않는다 → 남는 것은 PPTP, 모델에 따라 L2TP |
| ASUS RT-AC58U (안쪽) | WireGuard 없음 · OpenVPN은 710MHz ARM에 무겁다 · **뒤에 있어 포워딩이 두 겹**이 된다 |

**PPTP는 이 저장소의 확정 사항으로 쓰지 않는다.** 그래서 공유기가 다시 후보가 되는
경우는 **ipTIME에 L2TP가 있을 때 하나뿐**이다. 아니면 **NAS가 VPN을 진다** —
DS218+의 Celeron J3355는 AES-NI를 가지고 있어 이 일에 훨씬 적합하고,
공유기는 **포트포워딩 한 줄**만 맡으면 된다. 근거는 런북 03의 3·5절.

**문서 충돌이라 적어 둔 것은 충돌이 아니었다.** `njlee/REQUIREMENTS.md:199`는
**「범위 밖」 목록**에 있고 뜻은 "인터넷에 직접 열지 않는다"다. VPN은 사내망에
들여보내는 것이므로 "사내망 전용"이 그대로 성립한다. 문장을 뒤집을 일이 아니라
한 마디 덧붙일 일이다 — 어디에 무엇을 붙일지는 런북 03의 2절.

### 왜 2단계(리허설)를 먼저 두는가

개발 PC와 NAS의 **형태가 다르면 NAS에서만 나오는 버그가 생긴다.** 개발 PC에서 먼저
같은 구조(인스턴스 둘, PostgreSQL 17, 롤·`CONNECT` 분리)로 만들어 보면, 4단계에서
NAS는 이미 검증된 형태를 그대로 세우기만 하면 된다.

같은 이유로 결정 B에서 상시 staging 대신 **배포 리허설**을 택했다. 처음 해 보는 일을
운영 장비에서 처음 하지 않는다.

### 3번 — 처음 파악이 반대였다 (2026-09-02 정정)

계획서 초안은 "`njlee`의 백업이 NAS에서 안 돈다"고 적었지만, 실제로 읽어 보니

| `njlee/scripts/backup.ts` | `DATABASE_URL`로 TCP 접속 · 비밀번호는 `PGPASSWORD` | **이미 준비돼 있다** |
| `dss-auth/scripts/backup.ts` | `docker exec <컨테이너> pg_dump` | **돌지 않는다** |

`njlee`는 128행에 *"PG_BIN이 비어 있으면 PATH에서 찾는다 (NAS 컨테이너에서는
그쪽이 맞다)"*고 적혀 있다. 처음부터 컨테이너를 염두에 두고 쓴 코드다.
남은 것은 코드가 아니라 **이미지에 `postgresql-client-17`을 넣는 일**(3단계)뿐이다.

문제는 `dss-auth`다. `docker exec`를 부르므로 컨테이너 안에서는 돌지 않는다.
**돌게 만들려면 Docker 소켓을 앱 컨테이너에 물려야 하는데, 소켓 접근은 사실상
호스트 root 권한이다.** 하필 인증 컨테이너에 그걸 주는 것은 이 프로젝트가
인증 DB를 따로 격리한 이유를 정면으로 무너뜨린다.

→ **`dss-auth`를 `njlee` 방식(TCP + `PGPASSWORD`)으로 바꾼다.** 개발 PC에서
`docker exec`를 쓰던 이점(호스트에 클라이언트가 없어도 됨)은 모드 선택으로 남긴다.

비밀번호는 **셋이 아니라 다섯**이다. 앱 롤 셋(`AS_APP_PASSWORD`·`METERS_APP_PASSWORD`·
`AUTH_APP_PASSWORD`)에 더해, 상자를 세울 때 쓰는 부트스트랩 관리자 둘
(`APP_POSTGRES_PASSWORD`·`AUTH_POSTGRES_PASSWORD`)이 필요하다.
빈칸은 [`nas/.env.nas.example`](./nas/.env.nas.example)에 전부 있다.

아래 명령을 다섯 번 실행한다.

```
node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"
```

`base64url`인 이유: 이 값이 `DATABASE_URL` 안에 들어가는데, `@`·`:`·`/`가 섞이면
주소가 엉뚱하게 쪼개진다.

⚠️ **비밀번호는 상자를 처음 만들 때 굳는다.** 나중에 `.env.nas`만 고쳐도 이미
만들어진 롤은 바뀌지 않는다(초기화 스크립트가 빈 데이터 폴더에서만 돈다).
그래서 이 항목이 4단계보다 앞에 있다.

## 6단계에서 정할 것 — VPN 원격 접속 (2026-09-02 방향 확정)

**회사 밖에서 VPN을 통해 사내 시스템을 쓰기로 한다.** 인터넷에 앱을 직접 열지 않는다.

이 방향이 정해져 있으면 6단계 설계가 단순해진다 — VPN 사용자도 **사내 주소를 받으므로**
포털에 등록할 주소가 늘지 않고, 앱 설정을 하나도 바꾸지 않아도 된다.
`RF_Service_System/SECURITY_POLICY.md`에 원래 그렇게 적혀 있던 것이기도 하다.

**자세한 것은 [`runbook/03-원격-접속.md`](./runbook/03-원격-접속.md)로 옮겼다.** 여기에는 결과만 둔다.

착수 전 알아 둘 것 넷 중 **셋이 닫혔다** (2026-09-03).

| | 확인할 것 | 답 |
|---|---|---|
| 1 | 공유기가 WireGuard·OpenVPN을 지원하는가 | **둘 다 아니다.** 바깥 **ipTIME A2004NS-MU**는 WireGuard 지원 목록 밖 · OpenVPN 미지원, 안쪽 **ASUS RT-AC58U**는 WireGuard 없음 → 아래 |
| 2 | 회사 인터넷의 **업로드** 속도 | ⬜ **아직** — 이것이 남은 갈림길이다 |
| 3 | 밖에서 쓸 사람이 몇 명인가 | **3~5명** |
| 4 | **계측기도 밖에서 쓸 것인가** | **예 — 셋 다 VPN으로** |

> **앞서 적은 방향이 바뀌었다.** *"공유기가 지원하면 NAS 부담 없이 가장 깔끔하다"*는
> **공유기가 그 일을 감당할 때** 맞는 말이다. 여기 두 대는 그렇지 않다.
> 남는 프로토콜이 **PPTP**뿐이면 공유기 길은 닫힌다(⛔ 아래). 공유기가 다시
> 후보가 되는 경우는 **ipTIME에 L2TP가 있을 때 하나**다. 아니면 **NAS가 진다** —
> 공유기는 포트포워딩만 맡는다. 런북 03의 3·5절.

> ✅ **문서 충돌은 충돌이 아니었다.** `njlee/REQUIREMENTS.md:199`는 **「범위 밖」 목록**에
> 있고 뜻은 "인터넷에 직접 열지 않는다"다. VPN은 사내망에 들여보내는 것이므로
> "사내망 전용"이 그대로 성립한다. 정리 문장은 그대로 쓴다 —
> **"VPN으로 들어온 사람도 사내에 있는 것으로 본다."**
> 두 문서에 한 마디씩 덧붙일 자리는 런북 03의 2절에 적어 두었다.

⛔ PPTP는 쓰지 않는다. 설정이 가장 쉽지만 암호가 이미 깨진 방식이다.

## 나중에 반드시 확인할 것

**주소가 바뀌면 고칠 곳이 시스템마다 네 군데였다.** 지금은 개발 PC 안에서는
0군데다 — `.env.local` 은 `auto`, 포털 등록값은 `{lan}` 자리표시자를 쓰고,
둘 다 실행 시점에 그 기계의 실제 사내망 IPv4 를 찾는다.
판정 규칙과 근거는 `dss-auth/docs/주소.md`, 현재 상태는 포털에서
`npm run net:doctor`.

포털은 여전히 이 주소를 **글자 단위로 정확히** 대조한다. `{lan}` 은 비교
직전에 포털 자신의 주소로 펼쳐질 뿐이고, 와일드카드도 정규화도 늘지 않았다
(`dss-auth/src/lib/db/schema/clients.ts:32` 과
`dss-auth/src/lib/oidc/redirect-uri.ts` 에 그 이유가 있다).

### ⚠️ 7단계에서 물릴 자리 — 컨테이너 안에서는 `auto` 가 통하지 않는다

`auto` 와 `{lan}` 은 `os.networkInterfaces()` 를 읽는다. **브리지 네트워크로
띄운 컨테이너 안에서는 그것이 NAS 의 사내망 주소가 아니라 컨테이너의 주소
(172.17.x.x 같은 값)** 다. 그대로 두면 발급되는 ID 토큰의 `iss` 가 아무도
닿을 수 없는 주소가 되고, redirect_uri 는 어느 것과도 일치하지 않는다.

증상은 여느 때와 같이 "로그인이 안 된다" 하나뿐이므로, NAS 로 옮길 때는
**옮기기 전에** 아래 중 하나를 정해 두어야 한다.

| 방식 | 설정 |
|---|---|
| 리버스 프록시 뒤 도메인 (권장) | `OIDC_ISSUER=https://<도메인>` 직접 적고, 등록값도 그 도메인으로. `OIDC_ALLOW_HTTP_REDIRECT_URIS=false` 로 되돌린다 |
| 사내망 IP 로 계속 운영 | NAS 의 고정 IP 를 직접 적는다 (`auto` 를 쓰지 않는다) |
| host 네트워크로 띄움 | `auto` 가 그대로 동작하지만, 포트 충돌을 직접 관리해야 한다 |

어느 쪽이든 7단계의 "주소 갱신" 항목에서 `npm run net:doctor` 로 확인한 값이
실제 접속 주소와 같은지 눈으로 대조하고 넘어간다.
